# Correctly 5.13.4 — Release notes

## Fixed: text shortcuts in rich editors (WhatsApp Web, Gmail…)

- Text shortcuts now also expand in `contenteditable` fields (WhatsApp
  Web's Lexical editor, Gmail compose, simple rich editors), not only in
  `<input>` and `<textarea>`. Only a trigger inside the caret's own text
  node is replaced, through the browser's `insertText` (native undo, seen by
  the editor like typing); code editors, sensitive or non-editable areas are
  excluded. The trigger is selected, the editor is given time to see the
  selection (at most 50 ms), then the text is inserted; a key pressed
  meanwhile cancels the expansion and is never lost.

## Changed: confirmation dialogs (Text shortcuts settings)

- Deleting a shortcut and "Replace all" on import now ask in an in-page
  dialog styled like the settings page (Cancel focused by default; Escape
  or a click outside cancels), instead of the browser's `confirm()` box.
  Other settings pages still use `confirm()`.

- Tests: 37 files, 683 tests. Checked by the owner on WhatsApp Web with an
  equivalent in-page test; the release build itself not yet checked in
  Chrome/Brave nor with a real key.

## 5.13.3 — Release notes

## New: Custom formality (Reformulation)

- New rewrite style **Custom formality** with a 5-step slider from _Less
  formal_ to _More formal_: Light touch (keep the author's words and tone;
  only fix errors, smooth the sentence structure, read naturally), Relaxed,
  **Neutral** (default), Polished, Very formal.
- Available in the Reformulation tab, Translate & rewrite and the
  right-click panel; the slider shows while the style is checked and never
  sends anything by itself. Results are labeled with the level
  (e.g. "Custom formality · Light touch"). Still ONE AI request per
  Generate, whatever the styles chosen.
- Settings → Actions → Reformulation: starting level of the slider
  (`rewrite.formality`, default 3; invalid values read as 3).
- Messages: `formality` (1–5) is required with the `custom` style and
  refused without it (`isRewriteTextRequest`, `isTranslateTextRequest`).
  The worker passes the default level to content.js (`correctlyRun` 6th
  argument). No new permission, host or dependency.
- Tests: 36 files, 672 tests. Not yet checked in Chrome/Brave nor with a
  real key (owner checklist).

## 5.13.0 — Release notes

## New: English and French interface

- New setting **Interface language** (Settings → Getting started):
  _Automatic_ (follows the browser: French for a French browser, English
  otherwise), _Français_ or _English_. The settings page switches at once;
  already open web pages use the new language from their next opening of
  Correctly.
- Translated: the whole settings page (static text, messages,
  confirmations, errors, limits and statistics wording, dates and numbers),
  the in-page Correctly window and V5.2–V5.5 panel, the right-edge handle,
  the Undo toast, quota warnings and the right-click menu titles.
- Not translated on purpose: the instructions sent to the AI, the CSV/JSON
  statistics exports (data), model IDs and provider names. The browser's own
  command descriptions (chrome://extensions/shortcuts) stay in English.

## Under the hood

- Catalogs: `shared/i18n.ts` (shared wording), `content/messages.ts`,
  `options/messages.ts`; the static settings page is generated by
  `scripts/i18n-options.mjs` (French default text + `data-i18n` keys).
- Shared validation now returns codes (`ProviderError`, `ShortcutError`,
  range and key-combination problems) worded by the page; no French or
  English text is hard-coded in shared modules any more.
- Inline markup of the page (bold, keys, code, in-page links) is rebuilt
  node by node from an allowlist; no `innerHTML`.
- Settings schema: new `ui.language` (default `auto`); older settings read
  as `auto`. No new permission, host or dependency.
