## Implemented behavior

- **Translate:** a faithful, neutral translation, returned as one card.
- **Translate & rewrite:** the "Also rewrite in a style" box reuses the 7
  V5.4 styles. One request returns one card per ticked style.
- **Languages:** From is Auto-detect or one of FR / EN / AR / TR / DE / ES.
  To is one of the 6 languages, never Auto.
- **Arabic variants:** Modern Standard Arabic and Syrian colloquial. The
  variant picker shows only when To = Arabic, and its value is kept while
  hidden.
- **Same language:**
  - Choosing the same From and To disables the button, with "use Rewrite
    instead", and sends no request.
  - If Auto finds the text already in the target language, the model answers
    `same_language` in the same request and the panel says so.
- **Dialog and triggers:**
  - Right-click: **Correctly → Translate selected text…** and **Translate &
    rewrite…**.
  - The smart button gets a ⇄ action.
  - Shortcut `translate-selection`, with no key assigned by default.
  - The picker shows the privacy line "sent to Gemini only when you click
    Translate".
- **Safe Apply / Copy / Undo:** the V5.2 code is unchanged. Results are shown
  as text with `dir="auto"`, so Arabic renders right to left. This was
  confirmed in a real browser (C04: computed direction `rtl`).
- **Settings and migrations:** `correctly.v5.settings.translation =
{ source: 'auto', target: 'en', arabicVariant: 'msa' }`.
  - Each stored value is normalized when read. Unknown IDs fall back to the
    defaults, and Auto is never accepted as a target.
  - Translate & rewrite uses the existing rewrite default styles; no new
    style list.
- **Provider request accounting:** each Translate click is one attempt in the
  existing `UsageGuard`, with tokens recorded once. There is no separate
  detection call and no per-style call.

## API usage and privacy evidence

- **One-call verification:** unit tests show one `fetch` for neutral and for
  3 styles, and the worker test shows one call through the real handler.
  Detection happens in the same request.
- **Budget guard verification:** the same `generate()` path as V5.2 and V5.4
  (consent, key, cap reserved before dispatch).
- **Key isolation verification:**
  - The page receives only candidates. The worker sends the page the style
    IDs and language preferences, never the settings object.
  - A forged sender or extra keys get no reply and cause no network access.
- **Source content persistence policy:** nothing is stored. Tests check that
  storage holds no source text.
- **Prompt injection:**
  - Languages, variant and styles are validated against allowlists before
    they are put into the instruction.
  - The selected text is sent only as the `user` part.
  - The model's reply must be exactly `{status, candidates}`. Any extra field
    (for example `targetLanguage`) rejects it.

## Known issues and limitations

- **Unverified quality:** dialect accuracy and translation quality were not
  measured. The Syrian guidance is a prompt instruction, not a certification.
- **Arabic-Indic digits:** if the model writes ٣٥٠ instead of 350, the
  protected-token check sees a changed number and makes that card Copy-only.
  This is conservative by design.
- **Optional variants not built:** en-US/en-GB and other Arabic variants
  (Levantine, Egyptian, Gulf, Moroccan).
- **Options-page choices only:** the last choice made in the dialog is not
  remembered automatically, because the page must not write settings.
  Defaults are set in the settings page.
- **Smoke test:** in `--offline` mode, step M9 still sends one dummy-key
  request (issue carried over from V5.1, refused by Google at no cost).
