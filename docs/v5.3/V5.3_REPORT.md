## 2. Architecture

```text
toolbar click ─┐
Alt+Shift+C ───┼─► worker correctInTab(tab, trigger, frameId)
right-click ───┘     trigger enabled? key + consent? → executeScript(content.js, that frame)
                                                        │
smart button (smart.js, opt-in) ───────────────┐        ▼
                                               └─► correctInPage(document)   ← one per frame
                                                     capture → CORRECT_TEXT → worker
                                                     → UsageGuard → ONE Gemini call (V5.2)
                                                     → preview → Apply/Copy/Undo (V5.2)
```

- All four entry points end in the same `correctInPage()` and the same panel,
  stored in one isolated-world global, so a second activation while a request
  is in flight sends nothing (N4, P13).
- The worker keeps the only network path, the key, and the quota check (N10).
  The content scripts never read `chrome.storage`; that storage holds the key.

## 4. User experience

1. **Toolbar button**: works as in V5.2.
2. **Shortcut**: select text, then press **Alt+Shift+C**. Change it with
   Settings → **Change shortcut**, which opens `chrome://extensions/shortcuts`.
   The settings page shows the shortcut the browser actually assigned, or
   "not set". `Ctrl+Shift+C` was not used: Chrome reserves it for the DevTools
   inspector.
3. **Right-click**: select text in a text box or editor, then choose
   **Correctly → Correct selected text**. The correction runs in the frame you
   right-clicked. If that frame is embedded from another site, the top page
   shows "Correctly cannot reach this editor" and nothing is sent.
4. **Smart button** (off by default):
   - Turn it on in Settings, and accept Chrome's request for access to all
     sites.
   - A small ✓ appears inside the bottom-right corner of the focused plain
     text box. Clicking it keeps focus and the selection, then runs the same
     correction.
   - Turning it off removes the access, unregisters the script, and removes
     the button from open tabs.
   - It is only offered on `textarea` and `input[type=text]` fields that are
     not sensitive, read-only or disabled.

## 6. Security and cost

- Requests come only from an explicit activation. S01–S03 show zero calls
  while typing or selecting, and when the button merely appears.
- Synthetic clicks on the smart button are ignored (`isTrusted`), and its
  shadow root is closed.
- Plain page text is no longer sent (M02); only text boxes and editors
  qualify. Sensitive fields still get no button and no request.
- The worker accepts `CORRECT_TEXT` from any frame of a tab, but only from
  this extension's own content script (`sender.id`). Web pages cannot message
  the extension at all.
- Quota: unchanged. One `UsageGuard` in the worker covers every trigger.

## 7. Known limitations

- The smart button cannot be reached by keyboard. It is appended at the end
  of the page, so Tab order does not put it next to the field; keyboard users
  should use the shortcut. It is also not repositioned while a textarea grows
  as you type, only on scroll or resize.
- The smart button does not appear in `contenteditable` or rich editors, and
  not in iframes, because it is registered on top frames only. The shortcut
  and right-click menu still work there, with Copy only.
- The right-click entry shows on any editable field, even without a
  selection. In that case it explains that text must be selected and sends
  nothing.
- Revoking site access in `chrome://extensions` leaves the setting checked;
  the button simply stops appearing.
- Not built: a per-site disable list (no V5.1 basis), "current sentence"
  correction (no proven extraction in V5.2), and a UI language other than
  English.
