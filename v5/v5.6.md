## 0. Read every rule before writing code

### 0.1 Product decisions already agreed with the user

1. Correctly V5 is a **personal-use Chrome/Brave browser extension** built around Manifest V3 and a TypeScript frontend.
2. V5 must **not** require a localhost backend, a running Python service, Java, LanguageTool, an `.exe` server, or the legacy Windows installer.
3. Gemini/API-based **correction**, **rewriting**, and **translation** remain explicit user-triggered operations from V5.2–V5.5.
4. Text shortcuts are a **separate, local, synchronous-looking user feature**. Typing a configured trigger followed by an eligible separator expands it without a network call.
5. The user creates and owns the shortcuts. The extension must not silently create example shortcuts or upload a shortcut dictionary to Gemini.
6. Retain the documented V4 behavior and user data wherever safely possible, including up to **500 saved entries**, enable/disable, duplicates validation, case-insensitive matching, Unicode word boundaries, punctuation-aware separator handling, and local-only persistence.
7. V5.6 adds **JSON import and export**, with non-destructive previews, conflict policies, schema validation, and rollback/error recovery.
8. V5.6 adds **selective AI protection** for shortcut triggers and optionally replacements. This is NOT the same as keeping the entire extension offline: the user-requested selected text still goes to the AI in V5.2–V5.5.
9. No typing event, shortcut expansion, dictionary management action, or import/export may call a provider or consume an API quota.
10. Reuse V5.2–V5.5's safe editor adapters, disabled-site policy, security guards, undo machinery where applicable, and trusted background messaging.
11. Do not start V5.7 multiple providers/keys, V5.8 advanced usage limits, V5.9 dashboards, or V5.10 release hardening as feature projects.
12. Preserve the user's existing Git tree, dirty changes, data and historical versions. Never perform destructive migration without tested recovery.
13. A complete milestone requires tests and documented evidence; a successful build alone is not enough.

### 0.3 Key definitions, so implementation is unambiguous

- **Trigger:** User-defined short literal text, for example `cbj` or `bjr`.
- **Replacement:** Exact text inserted for a matched trigger, for example `Bonjour` or a longer signature.
- **Text expansion:** A local edit after the user types an eligible separator immediately after a whole-word trigger.
- **Separator:** The user-typed character that ends the trigger, e.g. ordinary space or comma. Preserve exactly one copy of it.
- **Eligible editor:** An editable surface for which the extension can prove a safe, exact replacement range.
- **Disabled entry:** Saved shortcut that never expands until re-enabled.
- **Disabled domain:** A site on which the user's existing Correctly policy prohibits feature execution.
- **Protect trigger in AI:** Prevent an **unexpanded** shortcut trigger inside deliberately selected text from being changed by AI, using temporary locally generated placeholders.
- **Protect replacement in AI:** Optional, explicitly enabled preservation of the resulting replacement text in AI operations. Disabled by default because common phrases like `Bonjour` might otherwise be frozen too broadly.
- **Plain text:** Rendered and inserted as text, never parsed as HTML, JavaScript, Markdown rendering instructions, or a privileged command.
- **Import preview:** Pure offline validation showing proposed changes before any data is written.
- **API operation:** User-initiated correction/rewrite/translation, not typing or text expansion.

## 2. User journeys: specific behaviors to implement

### 2.1 Create and expand a basic shortcut

1. Open Correctly extension settings.
2. Navigate to **Text Shortcuts**.
3. Select **Add shortcut**.
4. Enter trigger `bjr` and replacement `Bonjour`.
5. Save; a success message confirms durable local storage.
6. Open a test page with a supported `<textarea>` and type `bjr `, character by character.
7. Expected visible result: exactly `Bonjour `, with one trailing space.
8. The caret ends after the space; no duplicate characters; focus remains in the field.
9. Provider request count remains unchanged; the feature works with network disabled.

### 2.2 Punctuation and whole-word matching

- `bjr,` → `Bonjour,`.
- `bjr.` → `Bonjour.` if period is an accepted V4-compatible separator.
- `bjr!` → `Bonjour!` if `!` is supported by the inherited separator rules.
- `abjr ` → `abjr `, unchanged.
- `bjrXYZ ` → unchanged.
- `Salut bjr,` → `Salut Bonjour,`.
- `bjr` without a terminating eligible separator → unchanged while typing.
- A replacement containing punctuation must not duplicate the separator except where the literal replacement already intentionally ends with punctuation; the rule is always **replace trigger + keep precisely one typed separator**, not silently remove punctuation from the user's replacement.

### 2.3 Case-insensitive trigger and exact replacement casing

For stored `bjr → Bonjour`:

- `bjr ` → `Bonjour `.
- `BJR ` → `Bonjour `.
- `Bjr ` → `Bonjour `.
- Do not invent smart-case behavior. Replacement is inserted exactly as saved.

### 2.4 Enable, disable, edit and delete

1. Disable the entry with its row toggle.
2. `bjr ` must stay unchanged, with no network call.
3. Re-enable, retry, and confirm expansion resumes.
4. Edit replacement to `Bonjour à tous` and confirm the new text expands.
5. Delete requests confirmation; Cancel preserves the entry.
6. Confirm Delete removes only the chosen entry and persists after reload.
7. Existing entries are never silently discarded when adding or editing one item.

### 2.5 500-entry capacity and duplicate safeguards

- Accept up to 500 valid entries, including disabled entries.
- At capacity, prevent adding the 501st and show a helpful local message.
- Editing or deleting remains possible at capacity.
- Reject case-insensitive duplicates (`bjr` versus `BJR`) under the adopted V4 matching policy.
- Preserve V4 behavior around duplicate validation and ignore-case Unicode collisions.
- No sample entries should be seeded into a user's real dictionary.

### 2.6 Backup/export and safe restore/import

1. User selects **Export JSON**.
2. Browser downloads a UTF-8 JSON backup containing shortcuts plus schema metadata, but no API keys, prompt history, browsing data, or usage counters.
3. The user can inspect and keep the file offline.
4. User selects **Import JSON** and picks a backup file.
5. Import is parsed and validated **without modifying existing entries**.
6. UI shows how many entries are valid, duplicate, conflicting, skipped, updated, or new.
7. User explicitly chooses a conflict policy and confirms.
8. A successful import is an all-or-nothing logical change; invalid import leaves the original dictionary intact.
9. Re-importing the same file must not create repeated entries.

### 2.7 Shortcuts are not an AI command

Typing `cbj ` expands according to locally configured mapping. The expansion itself never sends the string, the replacement, or any context to Gemini. **Only if the user later explicitly selects text and invokes Correct/Rewrite/Translate** may that selected text be transmitted under the existing V5 rules.

### 2.8 Protected unexpanded shortcut when running AI

Suppose:

- Trigger: `cbj`.
- Replacement: user-defined string.
- AI trigger protection: enabled.

If the user selects `Please keep cbj unchanged.` and explicitly chooses Correct, Rewrite or Translate:

1. The system identifies whole-token occurrence `cbj` locally.
2. It constructs an **ephemeral protected placeholder** and temporarily substitutes it in the *request copy only*.
3. It sends the masked text and normal task instructions to Gemini, **never the user's entire dictionary**.
4. Every model candidate must preserve that placeholder exactly once.
5. The app restores `cbj` locally in the preview candidate.
6. The original editor is not touched until an explicit, safe Apply.
7. If the model damages, omits, invents or duplicates placeholders, mark that candidate invalid and disable Apply; do not run an invisible second paid request.

### 2.9 Optional protected replacement phrase

If the user deliberately enables **Protect replacement text in AI**, a saved expansion such as `Best regards, Alex` can be preserved verbatim in explicitly requested AI results. This is optional: common expressions like `Bonjour` may otherwise cause unnatural corrections or translations wherever they appear. Explain this in the UI.

### 2.10 Unsupported situations

- No active edit field: no expansion and no network.
- `input[type=password]`: never expand; never inspect contents.
- Read-only/disabled field: no expansion.
- Rich editor with nontrivial nested DOM: abstain from automatic changes if the existing editor adapter cannot prove safety.
- Browser extension page of another extension / restricted URL: do not bypass platform restrictions.
- Disabled domain: obey the product's existing disabled-domain behavior.
- Browser private/incognito profile: follow extension permissions and storage isolation; do not claim cross-profile sync.

## 4. Persistent data model and safe migration

### 4.1 Storage location and privacy contract

1. Preserve the documented `chrome.storage.local` approach, **per browser profile**.
2. Do not switch shortcuts silently to `chrome.storage.sync`.
3. Do not send shortcuts to a remote service, error tracker or analytics endpoint.
4. Do not store them in webpage `localStorage`; that is page-controlled and untrusted.
5. Do not mix personal Gemini API keys with exported shortcut dictionary data.
6. Clarify in UI that browser-profile removal may delete local storage; backups are user-managed.
7. Avoid claiming local storage is encrypted or inaccessible to anyone with access to the user's machine/profile.
8. Respect browser storage quota and provide non-destructive errors for quota failures.

### 4.2 Data compatibility requirements

- Discover real V4 schema before designing V5 migration.
- Preserve all valid V4 triggers, replacements, IDs if present, enabled states, and global switch settings.
- Do not trim or alter replacement text silently during migration.
- Preserve user intentional Unicode characters and line breaks in replacements.
- Add new protection flags with explicit defaults and document them.
- Keep migration idempotent: running it twice produces the same logical store.
- Record schema version; future V5.7–V5.10 changes must not need to guess formats.
- On malformed legacy records, keep original raw data in place and **stop destructive migration**; show repair/export guidance, not silent reset.

### 4.3 Proposed protection defaults

For **new or migrated** entries:

- `enabled`: preserve historical flag; if missing, follow verified V4 behavior, not guess.
- `protectTriggerInAi`: **true** by default. It affects only user-requested AI operations containing the literal trigger, not every typed character.
- `protectReplacementInAi`: **false** by default. Expose an optional per-entry toggle and a short warning.
- The global expansion toggle has no authority to override the user's **AI protection setting**, unless the UI explicitly documents a linked behavior. Prefer independent controls so disabled expansion can coexist with intentional AI-preserved terms.

### 4.4 Schema validation

For every entry validate at least:

- Known object shape; reject arrays, `null`, functions, and unknown dangerous nested structures in imported untrusted data.
- Stable, unique `id` or generate a safe new ID for imported legacy entries.
- `trigger`: nonempty string after using the established product's normalization policy; no embedded separators or newlines if V4 treated triggers as single tokens.
- `replacement`: string, not silently coerced; empty replacement allowed only if the existing V4 product contract explicitly supports it.
- `enabled`, protection flags: booleans only, or a *documented* migration default.
- No duplicated canonical trigger, even when IDs differ.
- No more than 500 total entries.
- Reject malformed Unicode/surrogates in imported records if they would corrupt matching; keep valid Unicode and emoji intact.
- Reject prototype pollution keys or use a strict object field picker; do not blindly spread arbitrary imported objects into state.
- Explicit length limits are required but must be chosen **after inspecting V4**; do not newly reject existing valid V4 data without a grandfathering/migration path.
- Never use `eval`, dynamic functions, or regex generated from user triggers without escaping and explicit validation.

### 4.5 Migration sequence

1. Read new-schema storage if present and valid.
2. If absent, probe only the known legacy storage keys discovered in code.
3. Read all legacy records; build a migration report in memory.
4. Validate/canonicalize a **copy**; detect conflicts and broken records.
5. If invalid: show recovery guidance, preserve the legacy blob, and stop writes.
6. If valid: write a **separate versioned key** or retain an immutable legacy backup, as the repository's architecture allows.
7. Read back and verify the saved record count and a content checksum/hash or deep equality.
8. Mark migration complete **only after** successful verification.
9. Test reload/restart and confirm idempotence.
10. Do not delete the legacy store automatically in V5.6. A later explicit cleanup can be proposed only with validated recovery.

### 4.6 Extension ID and browser-profile limitation

If the V5 extension has a different browser extension ID from V4, Chrome does **not** automatically expose V4's `chrome.storage.local` contents to V5. Do not pretend that an extension can read another extension's storage. Provide a user-controlled export from the old extension and import into the new one, or retain the same extension identity/profile if that is the user's chosen deployment path. Do not request privileged filesystem access to work around this.

## 5. Deterministic shortcut matching engine

### 5.1 No model is involved

Implement a **local deterministic algorithm**. Do not ask Gemini whether a trigger is present, whether a word is a shortcut, or whether to expand. No models, background HTTP services, or NLP libraries are required for these decisions.

### 5.2 Trigger eligibility preconditions

Before any expansion, assert all conditions below:

1. Global shortcuts enabled.
2. Current site/domain is eligible according to existing disabled-domain settings.
3. Active element is a supported editor of the existing V5 safe-edit adapter.
4. Active editor is enabled, not read-only, and not a known sensitive/secret input.
5. Latest event is a trusted **user typing** action that inserted one eligible separator.
6. Not in an IME composition session and not processing a composition update.
7. Not a paste, drop, autofill, browser undo/redo, React rerender, or extension-generated input event.
8. No active range selection being overwritten by a typing action, unless the editor adapter safely supports that exact case.
9. Caret and source text state can be read accurately before changing anything.
10. Relevant dictionary revision is current and validated.
11. A complete, enabled trigger ends **immediately before** the inserted separator.
12. Trigger begins at a legitimate word boundary using the validated V4-compatible Unicode logic.
13. The calculated UTF-16 offsets and current underlying editor content agree exactly.
14. The intended operation is idempotent and not already applied for this event.

If any check fails, return a **no-op**. Never try a speculative edit.

### 5.3 Matching semantics

- Trigger lookup is case-insensitive in the specific, documented sense inherited from V4. Avoid assuming English ASCII alone.
- Choose a single canonicalization function for storage validation, lookup, and import conflict checks. Inconsistent normalization creates invisible duplicate triggers.
- Unicode boundary support is mandatory; cover accents and non-Latin letters in tests.
- Match **complete literal triggers**, not arbitrary substrings, regex fragments or fuzzy synonyms.
- If trigger overlaps exist (`a` and `ab`), only the complete contiguous token at the cursor counts; do not match the suffix of a longer token.
- The original replacement is emitted verbatim, with no smart casing or implicit AI correction.
- Respect the V4 punctuation separator set after inspection. If adding supported separators, add acceptance tests and describe the behavior change.
- Do not expand when a separator is inserted inside existing words or text by clicking in the middle and typing.
- Do not expand just by moving the caret past a completed trigger.

### 5.4 Separator contract

A common implementation bug is losing or duplicating the typed delimiter. Use this exact conceptual transformation:

```text
BEFORE: prefix + trigger + separator + suffix
AFTER : prefix + replacement + separator + suffix
```

The `separator` is the literal character inserted by the user. The replacement may contain spaces or punctuation of its own; do not normalize the user's replacement in the editor transaction.

**Representative cases:**

| Typed input | Shortcut | Expected result |
|---|---|---|
| `bjr ` | `bjr → Bonjour` | `Bonjour ` |
| `bjr,` | `bjr → Bonjour` | `Bonjour,` |
| `abjr ` | `bjr → Bonjour` | `abjr ` |
| `x bjr!` | `bjr → Bonjour` | `x Bonjour!` (if `!` supported) |
| `BJR ` | `bjr → Bonjour` | `Bonjour ` |
| `bjr` | `bjr → Bonjour` | `bjr` |
| pasted `bjr ` | `bjr → Bonjour` | pasted content unchanged |
| typed `bjr`, then Tab | `bjr → Bonjour` | unchanged unless legacy V4 already supported Tab; V4 documented that it does **not** |
| typed `bjr`, then Enter | `bjr → Bonjour` | unchanged; Enter is **not captured** |

### 5.5 UTF-16 offsets, code points and graphemes

- The DOM Selection APIs and most JavaScript textarea offsets operate in UTF-16 code units; never mix them with Unicode code-point counts without an explicit conversion.
- Accented Unicode may have precomposed or decomposed forms; test both if the inherited matcher claims equivalence. Do **not** introduce normalization that changes saved replacement text.
- Emoji, skin-tone modifiers and zero-width-joiner sequences may occupy multiple code units or code points. Validate exact substring before replacing.
- Right-to-left Arabic text requires correct offset handling; cursor visual position differs from logical string order.
- Locale casefolding can be surprising in Turkish (dotted/dotless I). Document a deterministic policy and test it; do not promise language-neutral casefolding perfection.
- Reject malformed offset calculations rather than deleting an arbitrary number of characters.

### 5.6 Matcher pseudocode (logic sketch; adapt event timing)

```ts
function proposeExpansion(
  text: string,
  caretAfterSeparator: number,
  typedSeparator: string,
  dictionary: ReadonlyArray<ShortcutRecord>,
): null | { start: number; end: number; insert: string; expected: string } {
  if (!isSupportedSeparator(typedSeparator)) return null;
  if (!isSafeCaret(caretAfterSeparator, text)) return null;

  const separatorStart = caretAfterSeparator - typedSeparator.length;
  if (text.slice(separatorStart, caretAfterSeparator) !== typedSeparator) return null;

  const tokenRange = readWholePreviousToken(text, separatorStart);
  if (!tokenRange) return null;

  const typedTrigger = text.slice(tokenRange.start, tokenRange.end);
  const match = findEnabledExactCanonicalMatch(typedTrigger, dictionary);
  if (!match) return null;

  // Replace the trigger, not the separator. The already inserted separator stays.
  return {
    start: tokenRange.start,
    end: tokenRange.end,
    expected: typedTrigger,
    insert: match.replacement,
  };
}
```

**This is not copy/paste production code.** `readWholePreviousToken`, caret assumptions and event timing must be tested against the actual editor adapter and V4 behavior.

### 5.7 Never implement these shortcuts incorrectly

- Do not use `string.replace(trigger, replacement)` on the whole field: that could replace the wrong occurrence.
- Do not use unescaped user input in `new RegExp(...)`.
- Do not reconstruct an entire rich editor's HTML just to expand a token.
- Do not intercept Tab or Enter, which can disrupt form submission, indentation, accessibility and IME.
- Do not schedule an arbitrary timer that later rewrites stale text.
- Do not start any network request to “confirm” the trigger.
- Do not insert replacement with `innerHTML`.
- Do not silently grow the trigger dictionary with AI suggestions or text typed by the user.

## 6. Event handling and safe editor transactions

### 6.1 Discover the existing edit helper

Find the V5.2/V5.3 adapter that handles source snapshots, range validation, replacement, framework compatibility and Undo. **Prefer reusing it**, but verify it is appropriate for an *insertion triggered during typing*. Model-result Apply and synchronous text expansion are different actions; do not force them through a controller that waits on an API request.

### 6.2 Input and textarea event strategy

Use an event strategy compatible with the actual browsers and frameworks:

1. Observe `beforeinput`/`input` and composition events as supported.
2. Distinguish **human separator insertion** from paste, programmatic changes and composition.
3. Capture the expected post-insertion text and caret/range.
4. Compute local match against the current dictionary snapshot.
5. Immediately before edit, re-read editor content, selection, focus and disabled state.
6. If still identical, replace only the trigger substring using the supported range API/adapter.
7. Preserve the typed separator and trailing field content.
8. Set caret immediately after inserted replacement and already-present separator, or use the transaction result if framework-specific code requires it.
9. Dispatch only the input events necessary for compatibility with the host framework; guard against recursively expanding your own events.
10. Verify the result without storing the entire original input in persistent logs.

Potential safe editing APIs for ordinary controls include `setRangeText` and existing transaction helpers. Choose the one that passes actual framework browser tests; avoid assuming all frameworks update their internal state when a DOM property changes.

### 6.3 Contenteditable policy

- Support simple plaintext-like `contenteditable` elements through the already-tested adapter.
- V4 specifically limited new edits to simple single-text-node contenteditables and abstained from complex rich text DOM; preserve that caution.
- Only edit a contenteditable if a safe node/range snapshot can be proven, including offset checks and the exact trigger substring.
- Preserve surrounding formatting, hyperlinks and inline elements.
- If trigger spans multiple nodes or editor rewrites DOM during composition, **abstain** and leave text unchanged.
- Do not try to “fix” Gmail/Notion/ProseMirror/Slate/Quill complex structures via `innerHTML` or arbitrary document replacement.
- Existing V5.3 safe unsupported-editor behavior must remain intact for later AI operations.

### 6.4 Strong safety gates for sensitive fields

The shortcut controller must not inspect or modify:

- `input[type=password]`, one-time-code fields, or fields identified as credentials.
- Known payment/card/financial verification fields, sensitive autocomplete semantics and secret editors.
- `input[type=email]`, `url`, `search`, and `tel` if V4 excluded them from these new modifications; only expand scope with explicit tests/approval.
- Editors marked read-only, disabled or outside allowed site scope.
- Code editors and terminals where punctuation and trigger expansion may be destructive.
- Any `contenteditable` that the existing safe adapter explicitly refuses.

Read the actual V4/V5 exclusions; use a **conservative allowlist** rather than inventing broadly permissive behavior.

### 6.5 IME and language-specific composition

- Track `compositionstart`/`compositionend`, `isComposing` and relevant browser `inputType` values.
- Never expand during an active composition session.
- At `compositionend`, do not treat the result as a normal delimiter keystroke unless the tested event sequence proves safe; conservative default is **no expansion**.
- Ensure Japanese, Chinese, Korean, Arabic and accented input flows do not lose characters.
- Test at least one real IME when available; synthetic events are not a full substitute.

### 6.6 Paste, undo and programmatic events

- Paste of `bjr ` must remain the literal pasted string.
- Pasting text immediately after a trigger must not cause prior trigger expansion unless the user separately types a supported separator afterward and the exact match is newly eligible.
- Ctrl+Z/browser Undo must not unexpectedly trigger expansion.
- Undo semantics vary by editor and browser; do not falsely guarantee native Ctrl+Z everywhere. Prefer the existing transaction/undo architecture, and expose an explicit **Undo Correctly expansion** only if it can be implemented reliably without interfering with standard typing.
- If adding an explicit undo affordance, allow it only when the exact post-expansion text and editor revision remain unchanged, following V5.2 safety principles.
- Mouse events, focus, blur, selection changes, mutation observers, and DOM rerenders must never trigger expansion by themselves.

### 6.7 Prevent duplicate and recursive expansion

- Identify the input event/transaction currently being processed.
- Mark extension-originated editing as non-eligible for nested expansion.
- Two content-script listeners must not each perform the same replacement.
- Rapid typing (`bjr ,` or repeated spaces) must not result in two replacements.
- Debounce can reduce UI work but must **not** replace exact event-based eligibility.
- If an editor content update is asynchronously rejected by the host framework, do not endlessly retry. Report unsupported editor behavior in QA and degrade safely.

### 6.8 Performance targets and measurements

The old V4 supported up to 500 shortcuts. Continue supporting that scale:

- Precompute a map keyed by canonical trigger on dictionary updates; never scan 500 items for every keypress if a map suffices.
- Limit work to the active editor and recent token, not the entire document.
- Make event handling proportional to the trigger length, not the length of a 50,000-character field.
- Measure performance with 100, 5,000, and 50,000 UTF-16-code-unit documents and 1/100/500 configured shortcuts.
- Record **measured** p50 and p95 event handler duration in a reproducible benchmark. Do not assert an invented threshold was met without timing it.
- Avoid persistent logs of input text or replacement content.

## 8. Import/export specification (strict JSON contract)

### 8.1 Primary security principle

An import file is **untrusted input**, even when it has a familiar filename. It can be manually edited, corrupted, oversized, duplicated, or malicious. Validate in memory, display a preview, and perform **no persistent writes until confirmation**.

### 8.2 Proposed export shape

```json
{
  "format": "correctly-personal-shortcuts",
  "schemaVersion": 2,
  "exportedAt": "2026-10-15T12:00:00.000Z",
  "shortcuts": [
    {
      "id": "example-id-generated-at-runtime",
      "trigger": "bjr",
      "replacement": "Bonjour",
      "enabled": true,
      "protectTriggerInAi": true,
      "protectReplacementInAi": false
    }
  ]
}
```

The timestamp is an **illustrative format example**, not a requirement to hardcode that date. The example record should appear in documentation/tests only, not automatically in the user's real saved data.

**Export requirements:**

1. Stable format ID; exact schema version.
2. UTF-8 encoding, with Unicode preserved.
3. Deterministic item ordering and stable field names.
4. Only public shortcut fields needed for portability.
5. Exclude Gemini/OpenAI API keys, credentials, provider settings, API usage history, prompts, text selections, browser tabs, cookies and device identifiers.
6. Exclude internal untrusted runtime objects and functions.
7. Generate a safe filename such as `correctly-shortcuts-YYYY-MM-DD.json`.
8. Export only on explicit user action. Do not auto-upload anywhere.
9. Show a privacy warning if replacements could contain personal signatures, addresses or private messages.
10. Successful download/save initiation must not be mislabeled as cloud backup.

### 8.3 Export implementation options

For a user-initiated download, a `Blob`, browser `URL.createObjectURL`, and temporary anchor can be enough in an extension page. Investigate Chrome/Brave MV3/CSP constraints. Revoke object URLs and clean temporary elements. A downloads permission is not automatically necessary just to initiate a normal save. If the existing extension uses a permitted downloads API, document why.

### 8.4 Supported import formats

- Current V5.6 versioned export.
- Documented V4 export schema **only if one actually exists**; do not claim support for an invented V4 JSON format.
- An optional legacy parser may accept a verified raw V4 storage dump if needed, but it must be separately documented and tested.
- No CSV, XML, executable scripts, YAML or remote URL import required by default.

### 8.5 Import validation pipeline

1. User chooses a local `.json` file via file picker or file input.
2. Apply a safe byte-size ceiling based on 500-entry capacity and reasonable replacement lengths. Report oversized files before parsing; do not read unbounded files into memory.
3. Decode UTF-8; reject invalid encodings without mutating storage.
4. Parse JSON under `try/catch`; report syntax errors with no sensitive raw content in logs.
5. Require a recognized format identifier and supported schema version, or route through a verified legacy importer.
6. Validate `shortcuts` as an array and each allowed field strictly.
7. Validate 500-entry capacity after applying the proposed policy, not just incoming array length.
8. Detect duplicate canonical triggers **within the file**.
9. Compare incoming entries with the current stored dictionary using canonical trigger and stable identity policy.
10. Build an immutable dry-run plan with categories: add, identical/skip, conflicting, replace, invalid.
11. Display a preview with counts and clearly identified conflicts; do not reveal entire long/private replacement content unnecessarily in previews.
12. Ask user to choose the import conflict policy and confirm.
13. Re-read the store revision just before committing.
14. If store changed since preview, invalidate the preview and ask the user to review again.
15. Apply one validated updated dictionary store mutation, read back, and verify.
16. If write/verification fails, keep or restore the original validated state as safely as possible and surface the error.
17. Publish one settings update and show accurate outcome counts.

### 8.6 Required conflict policies

| Policy | Behavior | Safety |
|---|---|---|
| **Skip existing** (default) | Import only truly new canonical triggers, ignore existing ones | Safest default |
| **Overwrite existing** | Replace existing entries for conflicting triggers using explicit deterministic field mapping | Requires clear preview |
| **Replace all** | Replace entire stored dictionary with import content | Destructive; separate confirmation |

If import contains invalid records, default is **reject the file and leave storage unchanged**. A partial-import mode adds risk and is **not** required. If project conventions demand selective skipping, label it explicitly, preserve a complete original backup and test rollback; do not silently drop malformed entries.

### 8.7 Identity and conflict rules

- Compare canonical triggers for logical identity; never rely only on imported IDs.
- Imported IDs might collide with local IDs for different triggers; validate/regenerate safe IDs to avoid overwrite of unrelated records.
- When skipping existing entries, never mutate their flags or replacements.
- When overwriting, update exactly the intended matched trigger; declare whether local ID is retained. **Recommended:** preserve local ID for that logical entry.
- Import of exactly the current dictionary must be idempotent (no duplicated records, no unnecessary content rewrites).
- Stable revision handling prevents old UI tabs from silently overwriting a newer dictionary.
- If an imported entry conflicts by canonicalization but uses different Unicode byte representation, show the conflict clearly.

### 8.8 No secrets in backup

Explicit negative tests must assert all of the following are absent from exported bytes:

```text
API_KEY
AIza... (realistic secret-shaped fixture)
openai-secret-test-marker
providerCredentials
requestHistory
chatHistory
selectedPageText
browserCookies
```

Use **fake** secret markers in tests, never actual credentials. Do not collect a user's real key just to verify exclusion.

### 8.9 Backup recovery procedure

- Provide a help paragraph: keep the export file in a location the user controls; it contains potentially private replacement text; anyone with the file can read it.
- On invalid import: file is rejected, previous dictionary unchanged.
- On storage corruption: preserve raw blob and provide an explicit export/recovery path if safely feasible.
- On overwrite/import error: display concrete reason and recovery steps; if automatic rollback itself fails, stop changes and advise restore from the pre-import backup.
- If the browser has changed extension ID/profile, guide the user to export from the older installed profile and import the resulting JSON into the new profile.

## 9. Consistent storage writes and concurrent options windows

### 9.1 Why this is necessary

The V4 recap specifically documents that independent changes from multiple settings pages were merged and conflicting edits to the same entry were refused. Regressing to a whole-array blind write from each UI tab can **erase legitimate shortcuts**.

### 9.2 Required mutation model

1. UI sends a typed command (`add`, `edit`, `delete`, `toggle`, `import`), not a stale full dictionary blob by default.
2. The background/repository component validates request origin, shape and target ID.
3. It reads current state and revision.
4. It serializes updates initiated within the same extension worker instance in one mutation queue.
5. It detects conflicts against a per-record revision/fingerprint or validated expected state.
6. It writes and verifies the new canonical store.
7. It broadcasts a revision/change to subscribed views and active content scripts.
8. Separate settings windows reload and merge nonconflicting changes; conflicting same-entry edits require a visible resolution, not silent last-write-wins.

### 9.3 Important limitation: `chrome.storage.local` is not a database transaction

- `chrome.storage.local` has **no general compare-and-swap transaction** guaranteeing serializable concurrent writes across all contexts or worker restarts.
- A promise queue inside one service-worker instance serializes requests handled by that instance only; MV3 workers can suspend/restart.
- A revision field and reread reduce errors but do not magically create atomic CAS.
- To maintain the strongest practical guarantee for this single-user extension, centralize writes through one message-handling repository, avoid direct writes from Options/content scripts, use revision/conflict checks, and test multi-window interleavings.
- Document remaining rare races honestly rather than claiming impossible absolute atomicity.

### 9.4 Settings synchronization

- Use the existing message bridge and/or `chrome.storage.onChanged` to update in-memory dictionary snapshots.
- A content script may temporarily hold a stale snapshot during event delivery. Every proposed expansion should be revalidated against its local current revision and exact source text; when unsure, no-op.
- On service-worker restart, lazy-load a validated dictionary before accepting shortcut mutations.
- Do not send replacement contents to webpage `window.postMessage`, DOM attributes or untrusted page scripts.
- Restrict storage messages to trusted extension-origin senders; validate payload sizes.

### 9.5 Test the following concurrent scenarios

1. Two Options tabs add different triggers simultaneously; both survive.
2. One tab edits trigger A while the other toggles B; both survive.
3. Both edit A with different replacements; one commit wins and the other receives a conflict, never silent data loss.
4. One deletes A while the other edits A; stale edit must fail clearly.
5. Import preview is open while another tab adds an entry; applying stale preview requires rerun.
6. Service worker restarts between editing and saving; no corrupt store.
7. `chrome.storage.local` write is forced to fail; current dictionary remains recoverable.
8. Duplicate rapid Save clicks produce one record.
9. A disabled entry remains disabled after page reload and import/export round-trip.

## 10. AI protection: the critical integration with V5.2–V5.5

### 10.1 Problem statement

A user-owned abbreviation like `cbj` can look like a spelling mistake to an LLM. After the user intentionally requests correction, rewrite, or translation, the model might expand it incorrectly, delete it, translate it, or hallucinate a meaning. Sending the user's **entire** shortcut dictionary to explain abbreviations would waste tokens and expose unrelated personal phrases. **V5.6 must protect only the locally matched spans within the explicitly selected request text.**

### 10.2 Distinguish two independent concepts

**A. Local expansion at typing time**

- User types `cbj` and a delimiter in a supported editor.
- If expansion is enabled, the editor now contains the saved replacement (e.g. `Bonjour`).
- The trigger is no longer physically present in the editor. The extension must not invent tracking metadata across arbitrary browser edits to claim it remembers the origin of every character.
- If the user later selects the sentence for AI, the selection contains the replacement as ordinary text.

**B. Explicit AI request**

- User selects text and presses Correct / Rewrite / Translate.
- Identify protected literal triggers **still present** in the selected text, and optionally exact replacement phrases the user explicitly marked for protection.
- Mask those spans in the **request copy only**, restore them in the validated candidate after Gemini responds.
- Never alter source DOM during masking.

### 10.3 Default protection policy

- Protect **unexpanded triggers** by default for all enabled and saved entries with `protectTriggerInAi: true`.
- Do not protect every replacement phrase by default; `Bonjour`, `Merci`, `Thanks` or long general-purpose text would be overprotected in ordinary writing.
- Allow `protectReplacementInAi: true` for explicitly selected entries such as company names, signatures, private product codes, custom nicknames or fixed expressions.
- Keep the protection flags independent from whether expansion is enabled: a saved abbreviation might intentionally remain unexpanded inside selected text.
- Do not protect absent shortcuts. Never send unrelated dictionary entries with the prompt.
- The same protection policy applies to all candidates in multi-style rewrite and to translation with target language/dialect.
- Do not claim a generic LLM will always preserve every nuance of protected-token surrounding grammar; the user remains in control via preview.

### 10.4 Protection steps, exactly in order

1. Receive the **already approved** user-initiated AI operation and immutable selection snapshot from V5.3.
2. Require valid operation type (`correct`, `rewrite`, `translate`, `translatedRewrite`) and valid selected text.
3. Obtain the latest validated dictionary in privileged extension context. Do not trust arbitrary page-provided shortcut flags.
4. Build candidate match patterns from records whose appropriate protection flag is enabled.
5. Find literal whole-token trigger occurrences and optional exact replacement phrase occurrences in the **selected text only**.
6. Handle overlapping matches by a deterministic policy: prefer longer protected spans, then stable ID/order; never silently mask half of another protected span.
7. Generate a **fresh, unpredictable, collision-resistant per-operation placeholder namespace** in extension-controlled memory (crypto-grade randomness if available), plus a unique placeholder for every protected occurrence.
8. Check placeholder patterns do not already exist in the selected text. Regenerate on collision.
9. Build an ephemeral map `{placeholder → exactOriginalSubstring}`. Keep this in memory for the lifetime of that request only.
10. Replace matched spans in a **copy** of the request text with safe literal placeholder tokens.
11. Add a concise trusted model instruction: *do not change, delete, translate, split, or duplicate protected placeholder tokens; treat them as immutable text atoms*.
12. Reuse the existing V5.1 provider transport and the task-specific V5.2/V5.4/V5.5 schema/validation. **Exactly one user-requested generation call remains one call.**
13. After response parsing, validate each candidate includes each expected placeholder **exactly once**, with no unknown placeholder in the protected namespace.
14. If schema has a no-errors or unchanged status, validate that it is compatible with the masked/unmasked source semantics.
15. Restore exact original strings into the validated candidate **locally**.
16. Run the existing task-level validation on the restored result where applicable, including constraints against corrupt output and stale text.
17. Show only restored plain-text candidates in the existing unified preview.
18. Before Apply, the V5.2/V5.3 editor transaction revalidates source selection, focus, range and current content.
19. If any placeholder invariant fails, invalidate that candidate, show a clear error and keep original text untouched; no invisible automatic retry.
20. Release the ephemeral map and sensitive request contents from application memory as soon as practical; never persist mappings or full selected text in logs.

### 10.5 Example showing the masking boundary

Saved entry:

```text
Trigger: cbj
Replacement: My custom business phrase
Protect trigger in AI: true
Protect replacement in AI: false
```

Selected text:

```text
Hello cbj, can you reply tomorrow?
```

Example **local request copy**, not saved or displayed to the webpage:

```text
Hello CLY_PROTECTED_X7D93_01, can you reply tomorrow?
```

Gemini candidate:

```text
Hello CLY_PROTECTED_X7D93_01, could you reply tomorrow?
```

Validated local restored candidate:

```text
Hello cbj, could you reply tomorrow?
```

The actual placeholder namespace must be freshly generated and sufficiently unpredictable. The example marker above is illustrative, **not** a literal constant or a requirement to use that syntax.

### 10.6 Exact validation rules for each candidate

- No placeholder may be missing.
- No expected placeholder may occur more than once, unless the **source contained multiple occurrences**, in which case each source occurrence must receive its own unique marker and appear exactly once.
- No unknown marker in the operation namespace is permitted.
- Marker spelling/casing is case-sensitive and byte/code-unit exact.
- Partial, spaced, punctuated-inside, HTML-escaped, Markdown-escaped, or transformed markers must fail.
- Output cannot include a fabricated marker representing a value that was not in the selection.
- Candidate must satisfy the task-specific output schema and length bounds.
- Restore by **exact full marker lookup**, never heuristic substring repair or fuzzy matching.
- Render restored result with `textContent`/framework-safe text binding, never `innerHTML`.
- For rewrite with N styles, validate and restore each style candidate separately. One bad candidate must not cause automatic submission of another API request.
- If protection cannot be guaranteed for a requested result, explicitly say the suggestion could not be safely generated; allow Cancel and keep original. Do not silently show a dangerously altered proposal as safe.

### 10.7 Prompt injection and untrusted text separation

A webpage may contain strings like `Ignore previous instructions`, and imported shortcut triggers may deliberately look like instructions. Do not promote either to a privileged instruction. Keep operation settings controlled by code/typed enums, task instruction separate from user text, and output constrained by parser/validators. The preservation instruction concerns *generated marker tokens*, not arbitrary instructions embedded in source text.

### 10.8 Avoid exposing the dictionary or private expansions

- Do not attach JSON dictionary, shortcut metadata, or replacement mapping to Gemini.
- The only text included in the request is the user-selected material **minus locally masked spans**, plus minimal fixed instructions and task settings.
- User-selected unprotected content is still transmitted as part of the explicit AI operation: state this clearly in privacy settings.
- If a replacement was expanded into the editor before the user invokes AI and `protectReplacementInAi` is off, it is ordinary selected text and will be transmitted. Do **not** claim masking covers all sensitive content.
- Do not log original protected values, placeholder maps, API key, full prompts, or raw model responses.

### 10.9 Special cases to test

1. Two different shortcut triggers in one sentence.
2. Same trigger twice, each occurrence having a distinct marker.
3. Trigger adjacent to comma, period, apostrophe, accents or right-to-left punctuation.
4. Trigger as substring inside a larger word: no match.
5. Replacement is a multiline signature, with `protectReplacementInAi` on.
6. Replacement is common word `Bonjour`; protection off by default.
7. A replacement includes the trigger string itself; deterministic overlap resolution avoids nested infinite matching.
8. Trigger and replacement share text with another protected entry; longest-match policy.
9. AI returns uppercase/lowercase-modified marker → reject.
10. AI returns missing marker → reject.
11. AI adds an extra marker → reject.
12. AI duplicates an existing marker → reject.
13. AI puts markers in a different order during translation; acceptable only if each maps exactly once and task semantics remain reviewable.
14. Selected source contains an exact marker-looking string; regenerate marker namespace safely.
15. Correction reports `no errors` but returns incompatible modified text → reject under V5.2 response rules.
16. Rewrite produces 4 styles, one corrupt; safely reject that style while preserving valid independent candidates if UI contract supports partial success.
17. Translation French → Syrian Arabic with proper noun marked protected; preserve spelling exactly while allowing surrounding Arabic text.
18. Mixed RTL/LTR candidate preview renders safely without DOM injection.
19. Dictionary edited while API request in flight; the operation uses its original immutable mask map, not a newly changed dictionary.
20. User changes selected editor text during API latency; **Apply blocked** by existing stale-snapshot gate.
21. User cancels; no editor modification.
22. Browser service-worker restarts midflight; fail safely rather than losing map and applying unvalidated text.
23. Model output is huge or malformed; use parser/size guards and keep original untouched.
24. Protected literal exists only outside selected text; it must not affect the prompt or output.

### 10.10 AI protection integration points

Place protection **after** safe selected-text capture and **before** the already existing task prompt assembly/API call, with restoration **after** structured-output parsing and **before** preview emission. For V5.4 multiple styles, share the same per-request masking map across candidates. For V5.5 translation and dialects, preserve the target selection and settings exactly as chosen; masking must not force the output language to the source language.

A reference shape (adjust to actual project interfaces):

```ts
type ProtectionSession = {
  requestText: string;
  restoreCandidate(candidate: string):
    | { ok: true; text: string }
    | { ok: false; reason: 'missing' | 'duplicated' | 'unknown' | 'altered' };
  dispose(): void;
};

function createProtectionSession(
  selectedText: string,
  shortcuts: readonly ShortcutRecord[],
): ProtectionSession;
```

Never serialize `ProtectionSession` or its map to persistent storage. If the existing MV3 request pipeline crosses message contexts, keep only the minimal typed request envelope in trusted extension messaging; verify message sender and origin and keep the protection lifecycle tied to one request ID.

## 11. Interaction with quotas, network and future milestones

### 11.1 V5.6 operations that cost exactly zero API calls

- Typing or expanding a shortcut.
- Enabling or disabling shortcut expansion.
- Creating, editing or deleting an entry.
- Searching/filtering the shortcut list.
- Exporting or importing JSON.
- Validating a trigger or a backup file.
- Adding/editing protection flags.
- Loading settings or looking up protected spans locally.
- Rendering preview UI without clicking an explicit AI request action.

### 11.2 V5.6 operations that reuse an already requested model call

- Correction from V5.2 (one user call).
- One V5.4 rewrite generation that may return multiple styles.
- One V5.5 translation or translated rewrite.

Masking and unmasking do **not** add a second AI call. The existing V5.1 preliminary API limit/check and operation accounting remain in the network layer, not in the matcher.

### 11.3 Do not anticipate V5.7–V5.9 incorrectly

- Provider-specific APIs remain in V5.7; protection utility must not hardcode `Gemini` inside its matching logic.
- Full configurable per-day/week/month counts, threshold warnings at 80/95/100%, and stop logic belong to V5.8.
- Usage history and charts belong to V5.9.
- V5.6 may emit a local **feature event** for debugging or future integration only if it contains **no text** and does not create network telemetry. Do not silently create user statistics or spend limits as a side effect of shortcut typing.

### 11.4 No claims of perfect cost protection

A frontend-local cap cannot act as a provider-side hard guarantee if the API key is used elsewhere or storage is reset. Keep provider-side spending caps as separate protection and maintain documented behavior from V5.1; do not redesign billing here.

## 16. Security, privacy, and resilience audit checklist

### 16.1 Security of untrusted imported data

- [ ] JSON schema parser rejects wrong types, oversized input and dangerous keys.
- [ ] Imported text is never treated as markup, executable code, event handler, CSS injection or a URL to fetch.
- [ ] Replacement text in UI is escaped and inserted through safe text APIs.
- [ ] Imported shortcut triggers are not interpolated into an unsafe regular expression.
- [ ] Nothing in an import file can change provider endpoints, install permissions, enable secret logging or execute scripts.
- [ ] No file parsing failure results in a write or partial dictionary reset.

### 16.2 Privacy of selected text and expansion data

- [ ] Shortcuts remain in browser profile storage only.
- [ ] No shortcut dictionary sync/cloud export without an explicit user action.
- [ ] User sees a warning before exporting potentially sensitive replacements.
- [ ] AI masking does not send the entire dictionary or the local restore map.
- [ ] The protected marker is generated per request; plain source text is still handled under existing opt-in AI policy.
- [ ] Password/credential fields are excluded.
- [ ] API key cannot be read from page DOM, content script message reply, exported shortcut backup or logs.
- [ ] Logs use operation IDs/status codes, not source text, replacement values or complete AI output.

### 16.3 Failure resilience

- [ ] Read-only fallback when storage is corrupt.
- [ ] Undo/repair guidance after recoverable import failure.
- [ ] Safe no-op on uncertain editor offsets.
- [ ] Preserve unsaved form draft on network/storage error.
- [ ] No automatic billable retry when an AI protected-response candidate is malformed.
- [ ] No corrupted output applied after service-worker suspension.
- [ ] No destructive data cleanup in migration.

### 16.4 Manifest and CSP review

- [ ] No new local server host permission is required.
- [ ] Do not widen host permissions solely for text expansion.
- [ ] No `eval`, inline executable strings, remote script imports or CDN script dependencies.
- [ ] File input/export implementation is compatible with extension page CSP.
- [ ] Existing message sender authentication and routing are preserved.
