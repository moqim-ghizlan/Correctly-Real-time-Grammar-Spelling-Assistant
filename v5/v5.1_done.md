## 0. Source of truth, context, and interpretation

### 0.1 What exists today

The project's `recap_v4.md` dated 15 October 2026 describes:

- **V1–V2:** Chrome/Brave Manifest V3 extension with local LanguageTool checks.
- **V3–V3.1:** Python Windows launcher around bundled Java + LanguageTool; a Windows setup application.
- **V4 RC1:** text-expansion shortcuts, sentence-grouped corrections, guarded edits and undo, still connected to local port `127.0.0.1:8081`.
- Existing `frontend/` TypeScript code, `backend/`, `installer/`, `scripts/`, `docs/`, `dist/`, `artifacts/release/`; current root `npm run build`, `npm test`, `npm run lint`.
- Reported V4 automated coverage: 209 frontend tests and 64 backend tests; Chrome real-browser and some installed-Windows scenarios still require verification.

**Do not assume that every current file matches this summary.** Inspect the checked-out repository first. The repository files and running tests are authoritative for implementation details. The summary is context, not permission to delete uninspected code.

### 0.2 V5 product vision, versus V5.1 deliverable

**Final V5 direction:** Personal, frontend-only extension; no local Java, Python, LanguageTool or executable; LLM APIs on demand; eventually multiple providers, corrections, rewrite styles, translation/dialects, user-defined snippets, keyboard/context-menu/floating-button entry points, detailed limits/alerts/statistics.

**V5.1 ONLY** introduces the architecture and a working, narrowly scoped **Gemini connectivity smoke-test**. It is **not** the production writing assistant yet.

**Final V5 does not mean every future V5 feature ships in V5.1.** Preserve stable engineering boundaries while postponing unfinished features. Build a clean V5 foundation rather than packaging the V4 runtime and UI under a new number.

### 0.3 Decisions fixed for V5.1

1. **Personal use only**, on the user's own Chrome/Brave profiles.
2. **Frontend-only** in production: extension pages plus Manifest V3 service worker. **No custom cloud backend** and **no local server**.
3. Use **TypeScript** and **Manifest V3**.
4. **Gemini** is the only active provider in V5.1. Architect the interface for future OpenAI and other providers; **do not build them yet**.
5. The owner must be able to paste, test, replace, remove and locally save the **Gemini API key from extension settings**.
6. **All Gemini requests must originate from the extension service worker**, not a web page content script; no API key in the page DOM or request messages.
7. One deliberate **Test connection** action makes a minimal real API request. No background or automatic LLM requests while typing, installing or opening settings.
8. Add **initial local request guards and accounting** now, so later features do not depend on untracked traffic. Full daily/weekly/monthly per-action quotas and 80/95/100% alerts are **V5.8**.
9. Provide a **functional installation package consisting of extension files**, not Windows setup/EXE.
10. Keep V4 source/history safe. No irreversible removal of old release tags or user data.

### 0.4 Explicitly out of scope (do not implement)

- V5.2: real text selection, language detection, check-and-correct in one request, replacement, undo.
- V5.3: writing-field UI, floating button, context menu actions, keyboard correction shortcut.
- V5.4: professional/formal/friendly/funny/custom rewrite styles.
- V5.5: translation, Arabic dialects and saved language presets.
- V5.6: activation and migration of text-expansion shortcuts.
- V5.7: functional OpenAI/DeepSeek integrations and multiple stored keys.
- V5.8: complete daily/weekly/monthly quotas by action/provider, threshold notifications.
- V5.9: charts, per-day/week/month statistics and user-visible cost analytics.
- V5.10: final comprehensive release certification.

A placeholder reading “Coming in V5.x” is permitted only when it does not look clickable or imply a feature works. Prefer no unfinished navigation at all.

## 1. Definition of done — expected end result

The owner can:

1. Run documented install/build commands on a development machine with supported Node.js.
2. Load `dist/` as an unpacked **Manifest V3** extension in Chrome or Brave, with **no** Java/Python/LanguageTool/localhost listener required.
3. Open a polished **Settings** page with clear English labels (French localization may come later).
4. Paste a Gemini API key into a password-masked form, explicitly save it, close settings, reopen, and see **Configured** without seeing the raw key.
5. Press **Test connection** and receive `Connected` plus provider/model/timestamp **only when a real Gemini response succeeded**. If no valid key or service is available, see a specific, non-sensitive error.
6. Remove a key and see `Not configured`; subsequent connection attempts are blocked before network access.
7. Select a supported Gemini model **from an intentionally small, auditable list or discovered supported set**, save the preference, and test it (model availability must be checked live; do not assert a particular model is active just because it existed in a previous chat).
8. Observe a small **usage safety section** showing a **configurable local daily test-request maximum** (default: **20 attempts/day**, min 1, max 100) and the current local count. This is an implementation safety limit, **not** a billing guarantee.
9. See that the 21st test attempt (with a max of 20) is refused locally without contacting Gemini; a user can lower the cap but cannot bypass a reached cap by reloading the page.
10. See offline/timeout/invalid-key/quota/error states handled without freezing the UI or leaking credentials.

**Engineering acceptance:** clean builds, typecheck, lint, static bundle audit, automated unit and integration tests, at least one real-browser smoke test if browser automation is available, reproducible instructions, evidence report and no critical open bugs. No claim of live API validation without using an owner-provided key.

## 2. Non-negotiable security, cost, and privacy constraints

### 2.1 A browser extension is not a secure vault

`chrome.storage.local` keeps data inside the browser profile, but does **not** make a key impossible to extract from the local profile, browser debugging facilities, malware or a compromised extension. This is acceptable **only for personal-use BYOK** (bring your own key) with honest warnings. **Never embed a shared key in source or distributable builds.** Do not claim the key is encrypted or fully protected.

- Store in `chrome.storage.local`, never `sync` (avoid automatic cross-device replication).
- Never write the key to `console`, diagnostics, screenshots, telemetry, test snapshots, exception messages or Git.
- In settings, use `input type="password"`, with a controlled **Show/Hide** toggle; hide by default.
- When displaying status, show only `Configured` / `Not configured`; avoid displaying even masked key suffix unless needed.
- Explicit Save/Replace and Delete buttons; confirm destructive removal.
- Minimize sensitive state in page memory and clear input after successful save.
- Restrict extension host access to `https://generativelanguage.googleapis.com/*`. Never request `<all_urls>` for V5.1.
- Only allow predefined HTTPS Gemini API endpoints. **No arbitrary URLs or model paths accepted from untrusted page messages.**
- Do not expose the key to content scripts, injected scripts or websites. Keep all API calls in the service worker.
- Audit final built artifacts and `.gitignore` for secrets; test with fake sentinel keys.

### 2.2 Cost is never inferred from number of words alone

- Provider billing is based on **input/output tokens**, model-specific prices, and sometimes additional token categories.
- **No live background calls.** Every Test connection is explicit and **may consume quota / cost**.
- Display a concise notice near the button: “Sends a small test prompt to Gemini; may consume API quota or incur a small charge.”
- Show a link to Google's actual billing controls. Google project spend caps are experimental and may have ~10-minute enforcement latency; they are **not guaranteed exact ceilings**. See references at end.
- A local cap does not count calls from outside Correctly, another browser profile, deleted local data, or other keys using the same Google Cloud project.
- Avoid automatic retries, especially on 429/5xx: an unseen retry can incur cost or double-count quota.
- Limit test prompt and response lengths, timeout, and concurrency.

### 2.3 Privacy

V5.1 must only send a **fixed, innocuous smoke-test message** to Gemini, for example `Reply with OK only.` No user writing is sent yet. Do not silently transfer text from a tab, current selection, clipboard or browser history. Future V5.2+ must add deliberate consent boundaries around sending writing to cloud LLMs.

### 2.4 Basic threat model to record in docs

Document threats and mitigations: leaked key in bundle/log; malicious page spoofing messages; overbroad permissions; user-triggered request flood; lost network; damaged storage data; cross-profile state differences; model deprecation; accidental destructive migration; service worker suspension during a request.

## 5. Gemini API adapter — concrete implementation contract

### 5.1 Official API access

As of the research for this specification, the official Gemini REST API documents:

- Header: `x-goog-api-key: <key>`.
- Generate endpoint: `POST https://generativelanguage.googleapis.com/v1beta/models/{MODEL_ID}:generateContent`.
- JSON `contents` array containing `parts` with `text`.

Official: https://ai.google.dev/api and https://ai.google.dev/api/generate-content . **Revalidate endpoint/model availability at implementation time.**

### 5.2 Model selection policy

- Provide initial conservative model choice(s) only after checking current model availability for the owner's project/key.
- Do **not** hard-code a hypothetical future model or blindly assume `gemini-2.5-flash-lite` is available to every new account.
- The model must be allowlisted or validated against an official supported model list; validate IDs before interpolating them in URLs.
- Offer a useful “Model not available for this key/project” error rather than trying undocumented fallbacks.
- The default can be chosen from a **verified** current low-cost text model during implementation; document the exact chosen ID and verification date in `ARCHITECTURE.md`.
- Never switch from a cheaper to a more expensive model automatically.
- Do not implement multi-provider selection yet; represent provider internally as `gemini` so V5.7 can extend cleanly.

### 5.3 Example REST request for documentation/tests (never include a real key)

```http
POST /v1beta/models/{VERIFIED_MODEL_ID}:generateContent HTTP/1.1
Host: generativelanguage.googleapis.com
Content-Type: application/json
x-goog-api-key: <USER_KEY_FROM_LOCAL_STORAGE>

{
  "contents": [{"role":"user","parts":[{"text":"Reply with OK only."}]}],
  "generationConfig": {
    "temperature": 0,
    "maxOutputTokens": 32
  }
}
```

**Important:** Output token limits are not a precise dollar cap and model-specific reasoning tokens can affect observed output and billing. Do not assume the response always contains literal `OK`: validate structure, text presence and success; show a snippet with safe truncation, not the raw provider JSON. If the model declines or returns empty candidates, report `INVALID_RESPONSE`, not `Connected`.

### 5.4 Request path — step-by-step

1. Options UI renders `Not configured` until it loads configuration.
2. Owner clicks **Test connection**.
3. UI disables the button, shows spinner/progress, and sends typed `TEST_CONNECTION` message (no key in message body).
4. Service worker verifies trusted extension-message origin (`sender.id === chrome.runtime.id`), action literal, message shape and payload length.
5. Service worker reads locally stored settings and validates key, model and daily limit.
6. Under exclusive gate, check and **reserve** one local test attempt **before** fetch; record attempt timestamp, id, provider and category, without saving prompts/key.
7. Build hardcoded Google HTTPS endpoint from trusted model ID.
8. `fetch` with `AbortController`, e.g. 15-second timeout; send strict JSON and key header.
9. Interpret HTTP status, parse JSON defensively, extract short nonempty assistant text. Never return full headers or raw request.
10. Save completion status, available token usage metadata, and a normalized error category (if needed).
11. Return a strict DTO to UI with `ok`, status/error code, model name, timestamp, and optional usage metadata.
12. UI displays result and re-enables button (also on errors and timeout).

### 5.5 Safe response types (illustrative)

```ts
type ConnectionResult =
  | { ok: true; provider: 'gemini'; model: string; checkedAt: string;
      sample: string; usage?: { inputTokens?: number; outputTokens?: number } }
  | { ok: false; code: ErrorCode; message: string; retryable: boolean };

type ErrorCode =
  | 'NOT_CONFIGURED' | 'INVALID_KEY' | 'PERMISSION_DENIED'
  | 'MODEL_UNAVAILABLE' | 'RATE_LIMITED' | 'LOCAL_DAILY_LIMIT'
  | 'NETWORK_ERROR' | 'TIMEOUT' | 'PROVIDER_ERROR'
  | 'INVALID_RESPONSE' | 'STORAGE_ERROR' | 'UNKNOWN_ERROR';
```

The UI should display human-readable copy. Do not dump exception stacks. Map common HTTP outcomes cautiously: 400 may indicate invalid input/model, 401/403 credential or permissions, 404 model/path missing, 429 provider quota, 5xx provider availability. Read official error response where appropriate but **sanitize** descriptions before display or persistence.

## 6. Settings and local persistence — exact behavior

### 6.1 UI layout

**Header:** `Correctly V5.1` / `Personal AI connection setup` and small non-marketing scope disclosure (`Correction and rewriting arrive in later versions`).

**Section A — Gemini configuration:**
- Status indicator: `Not configured`, `Configured`, `Checking...`, `Connected`, `Connection failed`.
- API key field (`type=password`), `Show/Hide`, `Save key`, `Remove key`.
- Link to Google AI Studio key creation page; open as external HTTPS link with safe noreferrer/noopener behavior where applicable.
- Inline caution: “Personal-use API key; stored locally in this browser profile. Do not share this extension/profile or put a key in source code.”
- On replacement, do not delete previous key until new value validates structurally and user explicitly confirms Save. **Do not claim a key is valid until test succeeds.**
- On removal, clear key, last success status and sensitive transient UI state.

**Section B — Model:**
- Simple select: verified Gemini model(s) only; if one only, display a stable selected value.
- Explain “Availability and billing depend on your Google project.”
- If selected model is unavailable, retain configuration but show actionable error; never silently select a different paid model.

**Section C — Connection test:**
- `Test connection` button.
- Small notice about one small request / potential charge.
- Success result shows model and recent time.
- Failure shows understandable actionable guidance, e.g. `Invalid key — create or paste a valid key in Google AI Studio`, `Quota exceeded — check Google AI Studio`, `Offline — check internet`.
- Must not show API key, full raw provider error, or sensitive internals.

**Section D — Local safety limit:**
- Integer input `Maximum connection tests per day`, default 20, range 1–100.
- Read-only `Tests attempted today: N / limit`, `Remaining: X`.
- `Reset` is **not available** as a normal daily-cap bypass. Count resets automatically at next local date; local state remains best-effort and is not tamper-resistant.
- Later versions replace/extend guard with full feature-level quotas and notifications.

**Section E — Notes:**
- This build does not yet inspect or change text on websites.
- Future versions add correction, rewriting, translation, shortcuts, more providers, full statistics.
- Link to documentation and provider's billing/spend cap settings.

### 6.2 Storage structure (versioned)

Use a **single versioned settings schema**, with dedicated usage records; suggested shape:

```ts
interface V51Settings {
  schemaVersion: 1;
  gemini: {
    apiKey: string | null;
    modelId: string;
    lastSuccessfulCheckAt: string | null;
    lastSuccessfulModelId: string | null;
  };
  safety: { dailyTestAttemptLimit: number; };
}

interface DailyUsageRecord {
  schemaVersion: 1;
  localDate: string; // YYYY-MM-DD in the current local timezone
  testAttempts: number;
  completed: number;
  failed: number;
  inputTokensObserved: number;
  outputTokensObserved: number;
}
```

**Do not overwrite entire `chrome.storage.local`** on Save. Use namespaced keys so unrelated V4 data is not accidentally removed. Validate every loaded value and supply safe defaults for missing/corrupt values. Avoid keeping historical key contents in backups. If an existing V4 shortcut collection is found, do not delete it; V5.6 will evaluate migration.

### 6.3 Request counting semantics

- An **attempt** means a request that passes local guards and is reserved for dispatch. Count it even if the fetch fails, times out or the browser closes mid-flight. This is intentionally conservative.
- Clicking when no key exists does **not** create a dispatched attempt.
- Clicking after the local limit is reached does **not** increase the count and does **not** hit the network.
- Count successful responses only after validating a nonempty model answer.
- Provider rate limits are separate from local daily counts.
- Multiple simultaneous UI clicks must never reserve more than remaining capacity.
- Do not automatically retry ambiguous failures; show user-facing retry guidance.
- The timezone is the browser's current local timezone. Use an explicit, documented local-date function (e.g. `Intl.DateTimeFormat('en-CA', {year:'numeric', month:'2-digit', day:'2-digit'})` with stable part assembly). Do **not** slice `new Date().toISOString()` (UTC can shift dates). On timezone changes, reset behavior is best-effort; note this in tests/docs.
- For V5.1, ensure one authoritative serialized reservation path inside the service worker. Document that browser-profile storage is not a tamper-proof financial control, and that worker process restarts/rare concurrent contexts deserve testing. If true atomic updates cannot be guaranteed by the chosen storage primitive, use a conservative dispatch queue and never advertise strict monetary enforcement.
- Retain only the minimal current-day ledger in V5.1; V5.9 will add long-term statistics.

## 8. Detailed engineering work packages

For every work package: **implement → self-review → automated test → commit logically**. Commit messages are suggestions; never commit a real secret or unapproved unrelated work.

### WP01 — Baseline and branch safety

**Tasks:** phase 0 reconnaissance; capture baseline; identify current build test scripts.  
**Acceptance:** baseline report, safe branch/worktree, no untracked user work lost.  
**Typical failure:** overwriting current RC1 uncommitted files.  
**Remedy:** restore only agent-owned changes, choose worktree/branch; never hard reset user edits.

### WP02 — MV3 V5 runtime shell

**Tasks:** minimal manifest, service worker, options page, icon assets and version labels.  
**Acceptance:** unpacked extension loads without errors; options opens; no injected legacy UI.  
**Typical failure:** wrong output file paths, service worker import format.  
**Remedy:** inspect built manifest and browser extension errors; correct bundler entry mapping.

### WP03 — Typed configuration storage

**Tasks:** validation, defaults, key save/replace/remove, model save, schemaVersion handling.  
**Acceptance:** persist across close/reopen/browser restart; no key in `sync` or logs.  
**Typical failure:** race between UI initialization and storage load.  
**Remedy:** await initialization and disable unsafe actions until state is loaded.

### WP04 — Settings UX

**Tasks:** complete sections A–E, accessible labels, keyboard navigation, show/hide, confirmations, busy states, responsive width.  
**Acceptance:** no cut-off buttons at narrow browser sizes; screen-reader names; obvious result states.  
**Typical failure:** accidentally leave key visible while switching tabs.  
**Remedy:** default to hidden and clear transient reveal on navigation/unmount.

### WP05 — Service worker message gate

**Tasks:** typed message protocol, sender checks, response validation, error boundary, no secrets in UI↔worker messages.  
**Acceptance:** reject unknown actions and malformed payloads; no call for unconfigured key.  
**Typical failure:** service worker killed mid-request.  
**Remedy:** bounded request lifetime, persisted reservation and explicit user retry; no implicit replay.

### WP06 — Gemini REST client

**Tasks:** verified allowlisted model IDs, strict API URL, key header, minimal prompt, timeout, response validation, usage metadata extraction, normalized errors.  
**Acceptance:** success and all representative error fixtures pass; no key in logs/messages.  
**Typical failure:** treating HTTP 200 with empty candidate as success.  
**Remedy:** enforce positive response content validation.

### WP07 — Safety cap and accounting

**Tasks:** current-local-date record, attempt reservation, no parallel double-dispatch, configurable cap, counts in settings.  
**Acceptance:** exact local blocking behavior under unit/integration concurrency tests.  
**Typical failure:** `read → await → write` lost updates.  
**Remedy:** centralize all reservations and serialize dispatch; test races before release.

### WP08 — Legacy dependency audit and package

**Tasks:** remove active V4 runtime dependency, update scripts, build ZIP (optional), audit permissions and distributable artifacts.  
**Acceptance:** package works without localhost/Java/Python; no EXE bundled.  
**Typical failure:** stale `dist/` files reintroduced.  
**Remedy:** clean build from scratch and compare output manifest/file inventory.

### WP09 — Test automation and browser verification

**Tasks:** full matrix in section 9; capture actual commands and outputs.  
**Acceptance:** all automated critical cases pass, manual blocked cases called out.  
**Typical failure:** mocking too much and never testing MV3 message wake-up.  
**Remedy:** at least one real-browser service worker lifecycle test if environment allows.

### WP10 — Delivery and handoff

**Tasks:** README, setup instructions, key creation guide, billing warning, test report, commit summary, known limitations, acceptance checklist.  
**Acceptance:** another developer can reproduce from a clean checkout; owner only supplies personal key for real API smoke test.  
**Typical failure:** claiming implementation complete after unit tests only.  
**Remedy:** label each acceptance item PASS/FAIL/BLOCKED and link evidence.

### 9.3 Integration tests

### 9.4 Manual real-browser checklist

1. Clean build `dist/`.
2. Chrome: `chrome://extensions` → enable Developer mode → Load unpacked → select `dist/`.
3. Check displayed extension name/version and `Service worker` link/inspect view.
4. Open Settings. Confirm `Not configured` and default daily cap 20.
5. Save **dummy** test string, close/reopen settings; confirm masked configuration. Try Test and verify graceful failure without any key leaked. **Do not confuse dummy-key failure with a valid live API test.**
6. Remove key; confirm no request dispatch occurs without a key.
7. With a real owner-entered Gemini key, select a currently available model and Test connection **once**. Confirm `Connected` only on actual valid provider response. If key not provided, write **BLOCKED — owner credential required**, not PASS.
8. Temporarily set daily cap to 1 for manual test: first permitted, second blocked. Restore owner preference.
9. Kill/restart service worker from extensions page; reopen Settings; verify persisted values and one functional test if safe.
10. Reopen browser; verify config persists locally.
11. Open a regular site, type into inputs, verify **no V4 underlines, popup, floating button, text modifications or network calls**.
12. Disable internet; Test connection fails gracefully. Re-enable and recover.
13. Repeat core steps in Brave (`brave://extensions`). If Brave absent, mark BLOCKED.
14. Test screen width/keyboard focus and safe show/hide/password behavior.
15. Inspect developer consoles and Network panel: request goes to the approved Google HTTPS domain and key does not appear in console logs, content scripts or page-visible data.

## 10. Troubleshooting playbook — diagnose before modifying

| Symptom | Likely cause | Debug steps | Resolution | Regression check |
|---|---|---|---|---|
| Extension cannot load | wrong manifest path / invalid JSON | inspect `dist/manifest.json`, extension errors | correct build path/config | B01 + Chrome reload |
| Worker not found | wrong service-worker bundle | inspect manifest and dist asset | fix bundler entry | browser wake-up test |
| Settings white screen | missing asset/runtime exception | options DevTools Console + network | fix import/CSP/load | reopen twice |
| Key lost after restart | wrong storage, save race | inspect `chrome.storage.local` namespaced keys | await writes, re-read saved state | S02 + browser restart |
| Key in console | unsafe error logging | search output and code for logs | redact secrets; remove risky logging | N13 + B02 |
| 401/403 | key invalid, disabled API or project restriction | inspect sanitized status, project/key setup | guide owner, no hard-coded alternate key | N05 |
| 404 | stale/unavailable model ID | check Google's current model docs/list and selected account | use explicitly verified model | N06 + model selection |
| 429 | provider quota/rate limit | check status and AI Studio Usage/limits | show rate-limit message; no automatic retry | N07 |
| Network error in page | request sent from content script or missing host permission | inspect request origin/manifest | move fetch to worker, add exact host permission | B01 + integration |
| Service worker times out | long fetch/lifecycle | inspect worker DevTools and response path | bound request, persist attempt, explicit retry | N10 |
| `Connected` on empty output | lax response parser | replay fixture empty candidates | check candidate+text | N02 |
| Limit bypass with 2 tabs | storage update race | simultaneous message test | serialize reservations in worker | Q04/Q11 |
| Limit resets early | used UTC day instead of local date | timezone-edge test | local calendar day function | Q08/Q09 |
| Surprise charge | no provider-side spend cap / outside calls | check Google AI Studio billing and account/project scope | set provider cap; local cap is not exact money limit | documentation/security review |
| V4 correction appears | stale content scripts in manifest/bundle | inspect scripts + bundle inventory | deactivate legacy runtime | B04 + manual browser |
| Build contains EXE/Java | old packaging reused | inspect artifact manifest | create extension-only package | WP08 acceptance |
| Tests pass but live key fails | mocks hide real API mismatch | inspect sanitized real response, docs | correct API contract/model | live smoke test |

**Repair loop:** reproduce → isolate smallest failing test → fix root cause → rerun failing test → rerun full suite → rerun browser acceptance → document actual results. Do not work around errors by suppressing exceptions, disabling tests or downgrading security.
