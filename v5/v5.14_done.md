## 1. Contract

1. **No backend.** The browser syncs `chrome.storage.sync`; Correctly sends
   no request of its own. Permissions, hosts and CSP are unchanged
   (`storage` was already granted).
2. **Same ID everywhere:** `frontend/manifest.json` has a public `"key"`;
   `scripts/audit-dist.mjs` requires exactly that key, and refuses `.pem`
   files and private-key text in `dist/`.
3. **Local first.** Every feature keeps reading `storage.local`. Sync is a
   mirror, **off by default**, opted in domain by domain on each computer.
4. **Domains:** `shortcuts` (the list; "expansion on" stays local),
   `settings` (rewrite, translation, interface language, keyboard and
   right-click triggers), `keybindings` (the bindings; "on" stays local),
   `keys` (profiles + routes + keys, always encrypted).
5. **Never synced:** usage limits, journal and statistics (IndexedDB), the
   handle and its position, all-sites access, consent to send text, the
   legacy daily limit, V4 keys.
6. **Limits:** ≤ 7,000 bytes of data per chunk (Chrome: 8,192 per item),
   total budget 95,000 bytes (Chrome: 102,400). Over budget: nothing is
   written, error `tooLarge`, the local data stays whole.
7. **Never a silent loss.** Incomplete or corrupt data is never applied; a
   version replaced by a merge is kept in `correctly.v5.syncBackup` and can
   be restored; a newer format (`schemaVersion` > 1) is refused without any
   write.
8. Bilingual UI (fr/en); shared code returns codes (`SyncErrorCode`).

## 2. Storage

| Area  | Key                                     | Writer        | Content                                                        |
| ----- | --------------------------------------- | ------------- | -------------------------------------------------------------- |
| sync  | `correctly.v5.sync.meta`                | worker        | `{ schemaVersion: 1 }`                                         |
| sync  | `correctly.v5.sync.<domain>.head`       | worker        | `{ schemaVersion, rev, history[≤20], updatedAt, deviceId, chunks, hash }` |
| sync  | `correctly.v5.sync.<domain>.<rev>.<i>`  | worker        | `{ rev, data }` (chunk i of that revision)                     |
| local | `correctly.v5.syncPrefs`                | settings page | on/off and the four domain boxes                               |
| local | `correctly.v5.syncState`                | worker        | device ID, status per domain, bytes in use                     |
| local | `correctly.v5.syncBase`                 | worker        | last agreed head per domain (+ shortcut list for the merge)    |
| local | `correctly.v5.syncBackup`               | worker        | versions replaced by a merge (restorable)                      |
| local | `correctly.v5.syncSecret`               | worker        | key derived from the passphrase + its salt                     |

Chunk keys carry the revision, so two computers writing at the same time
never mix their chunks: a head always points to a complete set or to one
still arriving ("pending").

## 3. Decisions per domain (worker `background/sync.ts`)

Local payload L (normalized, canonical JSON), remote R (head + chunks,
hash-checked, then normalized by the existing `normalize*`/`parse*`), base B
(last agreed). R is a **successor** of B when `R.rev = B.rev` or B.rev is in
`R.history`; otherwise it is a **parallel** version.

- R missing → push L (an empty computer pushes nothing: no fake deletions).
- R incomplete → wait (a newer local edit is pushed anyway).
- L = R → agree. R unchanged since B → push L.
- R successor and L unchanged, or L empty → apply R.
- Both changed → shortcuts: three-way merge by shortcut ID against B
  (parallel version: against an empty base, nothing reads as a deletion);
  other domains: the side edited just now wins, otherwise the remote; two
  parallel versions are ordered the same way on every computer
  (`updatedAt`, then `rev`). The local version that loses is backed up.
- First activation, both non-empty and different (not shortcuts) →
  status `choose`: "Keep this computer's version" / "Use the synced version".

Loops are impossible: a write is made only when content hashes differ from
the base. One push = one `set()` (head + all chunks + meta), then the old
chunks are removed.

## 4. API keys

PBKDF2-SHA-256, 600,000 iterations, 16-byte random salt → AES-GCM-256,
12-byte random IV per push; envelope `{ v, kdf:{name, iterations, salt}, iv,
ct }`. Wrong passphrase → `badPassphrase`, nothing changed. Another salt →
`locked` ("Unlock" on that computer). "Use a new passphrase" re-encrypts this
computer's keys and replaces the synced ones (confirmation). The derived key
stays in `storage.local` (TRUSTED_CONTEXTS), next to the keys themselves.

## 5. Messages (settings page → worker, trusted sender only, exact shapes)

`correctly.v5.syncNow`, `syncClear`, `syncResolve {domain, keep}`,
`syncRestore {domain}`, `syncPassphrase {passphrase ≤ 1024, mode}` →
`{ ok: true } | { ok: false, code }`.

## 6. Out of scope (next milestone if needed)

Compression of large shortcut lists, syncing limits, a Correctly backend.
