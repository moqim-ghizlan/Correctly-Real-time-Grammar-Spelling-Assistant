## 0. Mission and mandatory agent behavior

### 0.1 The goal in one sentence

Build an **honest, local-only usage and cost dashboard** on top of the V5.8 quota journal and the V5.7 multi-provider dispatcher, showing what happened without initiating additional paid AI calls, collecting private text, or corrupting any quota counters.

### 0.2 Essential sequencing rules

1. **Inspect** the current repository, git status, branch, tests, extension manifest and existing V5.8 IndexedDB schema before changing code.
2. **Write down** the current implementation's real field names and storage contracts. The plan's TypeScript snippets are *reference contracts*, not instructions to overwrite real types.
3. **Establish baseline** test results and archive them. Separate pre-existing failures from new regressions.
4. **Implement pure calculations and contracts first**, then durable aggregation/telemetry, then migration, then UI, then end-to-end verification.
5. **Protect hard quotas first**: the analytics observer must not become a gatekeeper, alternate dispatcher or new route to a provider.
6. **Do not modify or recreate prior user-generated data** without a versioned migration and rollback/recovery tests.
7. **Never replace missing usage with zero** when provider metadata or historical coverage is unavailable. `Unknown` and `0` are different facts.
8. **Never backfill fake timestamps, success labels or token totals** for prior history.
9. **Every metric is defined and testable**: unqualified words such as 'corrections' or 'savings' are forbidden where they would confuse requests, suggestions and actual edits.
10. **No claim of completion without evidence**: tests actually run, failures, browser checks, storage migrations, cost fixtures and security checks must be reported.

### 0.3 Product guarantees that may not change

- Personal-only Manifest V3 extension written in TypeScript; Chrome and Brave are targets.
- There is **no Correctly backend** and no local Java/Python/LanguageTool server or EXE installer.
- The owner supplies their own Gemini/OpenAI API keys through extension settings; V5.7 owns secret storage and model/task routing.
- AI requests happen **only after an explicit user action**, never continuously while typing or simply opening the dashboard.
- V5.2 checks and proposes corrections in one model-generation attempt.
- V5.4 generates multiple rewrite styles in **one** attempt when they are in one provider request.
- V5.5 translates and handles target language/dialect, including Syrian Arabic, without hidden extra generations.
- V5.6 shortcuts remain local/offline/free and are protected against unwanted AI rewriting.
- V5.3 preview, Apply, Copy, Cancel, Undo and stale-editor protections stay intact.
- V5.8 request caps count **possibly billable generation attempts**, with atomic durable reservations, scope intersections, day/week/month windows, and 80/95/100% alerts.
- Gemini/OpenAI switches, key rotation and multiple tabs **cannot reset global usage**.
- V5.9 is **read-only with respect to enforcement state**; only its own analytics snapshots, local action event records, price configuration and retention controls may be added or updated.

### 0.4 Explicitly in scope

- A dedicated **Statistics** area in extension options and a compact, clearly labeled popup summary if current UI architecture permits it.
- Date presets **Today**, **This week**, **This month** and a **Custom range** of calendar dates.
- Clear distinction among generated attempts, successful model results, correction outcomes, previewed proposals, applied edits and rewrites/translations.
- Breakdown by task, provider, model and stable credential profile ID/display label.
- Time-series charts and accessible text/table equivalents.
- Provider-reported token counts where available, with missing/partial counts clearly indicated.
- Configurable/versioned **USD pricing references** per documented model and usage category; local estimated cost only when inputs support calculation.
- Safe statistics export (CSV and/or JSON) and **explicit, confirmed local history deletion**, designed to preserve active quota enforcement and API keys.
- Reasonable historical retention and metadata minimization, plus honest partial-history warnings.
- Compatibility/migrations with V5.7 and V5.8 and full regression tests.

### 0.5 Explicitly out of scope

- New provider support or undisclosed model auto-switching; V5.7 owns that.
- Request-limit refactor or new billing hard stops; V5.8 owns quota admission and enforcement.
- Retrieving provider invoices, billing balances, bank charges, FX exchange rates or live prices from an undocumented endpoint.
- Any external analytics, cloud dashboards, account login, sync, background paid model calls or telemetry collection.
- Automatically importing old user texts, email content, web URLs, prompts, output candidates, API keys or shortcut dictionaries into statistics.
- Claims of token-perfect or invoice-perfect cost, discounts, taxes, subscription credits or provider remaining balance.
- Paid probes solely to obtain token pricing or quota information.
- Automatic correction/rewrite on every keystroke.
- A new free-for-all data ingestion endpoint exposed to website JavaScript.
- A large user-behavior surveillance feature (website-by-website statistics, field names, selected-text length trails or clipboard contents).

### 0.6 Priority order in case of conflicting goals

1. No data loss, privacy breach or quota bypass.
2. Correct, explicit definitions of metrics and numerical accuracy.
3. Migration/backwards compatibility.
4. Responsive and accessible UX.
5. Cosmetic polish and optional data visualizations.

When the agent cannot meet priorities 1–3, **stop and report `NOT READY`**, not a polished dashboard built on unreliable measurements.

## 3. User-facing information architecture and UX flows

### 3.1 Position in extension options

Suggested navigation (adapt existing UI instead of building a separate framework):

```text
Correctly — Settings
  ├── General
  ├── AI Providers & API Keys
  ├── Correction / Rewriting / Translation
  ├── Text Shortcuts
  ├── Usage Limits       (V5.8 — enforcement controls)
  └── Statistics         (V5.9 — reporting only)
```

The **Usage Limits** page should not be removed or replaced by Statistics. It tells the owner how many requests are **allowed**; Statistics tells them what requests and outputs were **observed**. Link between them without making either the sole source for the other.

### 3.2 First launch, no AI requests yet

- Show `No AI requests recorded in this period` in the activity chart and count widgets when the analytics store is genuinely empty and healthy.
- Show estimated cost as `$0.00` only when there really are **no attempted requests** in the selected period; do not show zero because pricing is missing.
- Optional short hint: `Statistics stay on this device. Make a correction or rewrite to see activity.`
- No permission request, key validation request or provider call simply to view statistics.
- Changing date preset should update the local view without writing to quota counters.

### 3.3 Basic usage scenario

1. User performs a correction from V5.3.
2. V5.8 atomically reserves/adopts the correct request counter entries.
3. The provider generation call runs once.
4. Normalized metadata (task/provider/profile/model, time, outcome, tokens when reported) is persisted without text.
5. If the result is displayed, it is a **completed AI correction check**, regardless of whether the user applies an edit.
6. If the user clicks Apply and the original editor text is successfully and safely updated, record a **correction applied** event. If Apply is denied as stale, do **not** increment applied count.
7. Refresh Statistics and show request, successful check, applied action and provider token coverage accurately.
8. Do not send another generation to calculate the numbers.

### 3.4 Four rewriting styles in one request

One request might return `Formal`, `Professional`, `Friendly`, `Funny`. Display:

- **1 generation attempt** (V5.8 quota semantics).
- **1 successful rewrite request** if provider output passed parser/semantic validation.
- **4 proposed variants** *only if* the application already has reliable count metadata and the UI explicitly explains the meaning of candidates.
- **0 applied rewrites** until a specific proposal is actually inserted into the editor.
- **1 applied rewrite** after a single Apply succeeds, regardless of how many variants were produced.
- **No extra AI cost** merely for selecting, previewing or copying one of the generated outputs.

### 3.5 Translation and dialect workflows

- Translation into Syrian Arabic counts under existing `translation` task key.
- One combined French→Syrian-Arabic rewrite counts under `translate-and-rewrite` when sent as a single model request.
- Avoid tracking the text itself, detected dialect inside private content, recipient names or document titles.
- Do not invent a separate translation attempt if the V5.5 request already classifies the combined task.

### 3.6 Limit reached

- After the quota reaches 100%, the next blocked attempt is **not** a generation attempt because the provider was not contacted; the dashboard may optionally show `blocked locally` in a separate series.
- Display `Requests used: N` according to V5.8's counted policy, independent of whether provider metadata exists.
- A local block has zero generated tokens and no API cost *for that blocked action*, but do not treat the entire period's missing token data as free.
- Statistics UI cannot reset counters by resetting a graph or clearing cached summary rows.

### 3.7 Network timeout and retry

- First request possibly sent, then times out: **one counted generation attempt** with unknown billing outcome and usually unknown tokens.
- User deliberately retries: **second** separately counted attempt.
- Show both attempts, mark at least the first as unknown, and do not present the price of the first as definitively `$0.00`.
- No retry, polling or provider calls from Statistics.

### 3.8 User with several keys / two providers

- Two Gemini keys and one OpenAI key may be present.
- User can group by provider, model, credential profile or task.
- A profile shown as `Gemini personal` is a **local display label**; history must use a **stable non-secret profile ID**, not a raw key or user-editable label.
- Deleting/renaming/rotating a key must not erase its past attribution or mutate historical prices.
- If profile label no longer exists, show `Deleted profile (id suffix)` or a sanitized stable placeholder; avoid exposing the full original secret.

## 4. Definitions, units, and accounting truths

### 4.1 Required dictionary

| Name | Definition | Important nuance |
|---|---|---|
| Generation attempt | An operation marked possibly-sent by V5.8 before provider fetch | May cost money even on error/timeout |
| Reserved operation | Permit acquired but not yet committed to send | Counts against available capacity while in progress, not historical sent usage |
| Local denial | V5.8 blocks before provider send | Not a generation attempt |
| Successful model response | A provider reply parsed and validated for the requested task | Can still be a `no errors found` correction |
| Correction check | Successful V5.2 operation, error/no-error result | Do not call this `errors fixed` |
| Correction proposed | A valid proposed changed version offered to owner | May be refused/not applied |
| Correction applied | Safe edit actually committed to target field | Is not inferred from provider success |
| Rewriting generated | Successful V5.4 operation with validated style variants | Four variants can be one generation |
| Rewriting applied | Selected rewritten variant successfully inserted | Do not count Copy as Apply |
| Translation generated/applied | Equivalent V5.5 generation/application semantics | Combined task stays distinct |
| Undo | Successful reverse of an applied edit, not an API event | Reporting policy must explicitly say gross vs net applications |
| Token usage | Usage metadata reported by provider adapter | Does not necessarily equal billable units or precise invoice |
| Price reference | Owner-provided or verified, timestamped USD rate per 1M tokens | Not necessarily live, current or applicable to old usage |
| Estimated API cost | Locally computed approximation for priceable observations | Distinct from actual provider billing |
| Unknown/partial coverage | No complete trustworthy data for some operations | **Never** assume zero |
| Historical coverage | Extent of dates/fields actually available | Migration may leave gaps |

### 4.2 Metric labels that MUST NOT be conflated

Use separate UI terms:

- **Requests used** = committed/possibly-sent generation attempts, exactly as V5.8 defines them for quotas.
- **Successful AI operations** = validated model outputs, not the same as number of requests.
- **Corrections checked** = correction operations with successful validated response.
- **Changes applied** = editor insertions confirmed successful by the client, if reliable local events exist.
- **Rewrites generated** = successful rewrite operations; multi-style generation is still one.
- **Rewrites applied** = one successful selected-text replacement (not one per candidate).
- **Translations generated** and **Translate + rewrite generated** = independent task categories.
- **Input tokens reported** and **Output tokens reported** = sum *only* over observations reporting those fields.
- **Estimated cost (USD)** = sum over observations for which enough priceable metadata and a valid price entry exist; if others are missing show partial + unpriced count.

### 4.3 Unqualified total counts are dangerous

Examples that MUST be rejected or clarified:

- `100 corrections made` from 100 V5.8 `completed` operations: no proof edits were applied.
- `5,000 requests = $2`: count alone cannot determine token cost.
- `No token metadata means 0 tokens`: logically false.
- `No successful response means free`: potentially false.
- `4 selected tones = 4 generation requests`: violates V5.4/V5.8 contract.
- `Copy a response = Apply it`: false.
- `A user-visible Undo cancels the bill`: false.
- `Reset statistics = Reset your daily cap`: prohibited.

### 4.4 Equality invariants

For a chosen range and compatible event history:

- `attempts = successfulAttempts + failedAfterSendAttempts + pendingOrUnknownSentAttempts` **only if** all mutually exclusive final states were reconciled and no history is missing; otherwise show a discrepancy/unknown state.
- `totalByProvider = sum(disjoint provider groups)`, including `Unknown`, based on **unique operation IDs**.
- `totalByTask = sum(disjoint task groups)`, including `Unknown` if mapping is unavailable.
- `global requests = number of unique committed possibly-sent operations`, **not** sum of global + per-task + provider + profile quota rows.
- `confirmedApplies <= total valid Apply events`; it is possible to apply multiple times from one generation only if the actual UI allows it; never force an unjustified equality.
- `undo count <= successful undo events` recorded; report gross applications and undos distinctly instead of subtracting price or attempts.
- `priceableObservations <= tokenReportingObservations <= countedSentObservations` as a typical consistency expectation for countable operations; note atypical provider non-generation metadata and field-level partial coverage may require a more nuanced contract.

## 5. Canonical data sources and relationship to V5.8

### 5.1 Choose a single source of truth for attempted requests

**The V5.8 durable ledger is authoritative for attempted AI generation.** The analytics dashboard must NOT create a second 'requests sent' counter and pretend it overrides the quota engine.

Suggested flow (logical, not necessarily exact source files):

```text
Explicit user action (V5.3 / V5.4 / V5.5)
       |
       v
Privileged task dispatcher (V5.7)
       |
       v
V5.8 atomic admission + possibly-sent commit ---> canonical attempt record
       |
       v
Gemini / OpenAI HTTP generation
       |
       v
V5.8 settlement + normalized provider usage
       |
       +----> V5.9 local, idempotent reporting projection
       |
       v
Existing result preview / Apply / Cancel / Undo
       |
       +----> V5.9 local non-text Apply/Undo event (only if action actually succeeds)

Statistics UI --> read-only query API --> indexed local analytics -> screen/export
```

### 5.2 Existing V5.8 data model must be respected

The V5.8 plan includes example stores:

- `quotaPolicy` — policy and timezone.
- `quotaCounters` — dimensions × day/week/month for quota enforcement.
- `quotaOperations` — unique operation IDs, route IDs, task, state, timestamps, token usage if reported.
- `quotaAlertOutbox` — deduplicated threshold warning delivery.
- `quotaMigration` — versioned migration state.

These names are **specification examples only** until confirmed in code. The agent must inspect real existing stores/indexes and should add analytics-specific stores rather than rewriting the quota engine to suit graphs.

### 5.3 Never sum overlapping dimensions or overlapping period levels

One correction operation can increment global-day, global-week, global-month; task-day/week/month; provider-day/week/month; profile-day/week/month, etc. Consequently:

**WRONG:** add global daily + task daily + provider daily to get total requests.  
**RIGHT:** count **one canonical operation ID once**, then group by one disjoint attribute at a time.

Similarly, summing `week` totals plus `day` totals double counts. Choose one canonical aggregation grain and documented reconciliation process.

### 5.4 Distinguish quota snapshots from historical reporting

- V5.8 counters are optimized for fast admission and may be current-window aggregates; they are not necessarily a full permanent event history.
- V5.9 should maintain a separate, bounded, materialized **daily reporting series** keyed by calendar day/timezone and immutable attribution, plus recent operation metadata for exact custom ranges and debugging.
- If V5.8 already compacts older records, use its verified historical aggregate data only to the specificity it actually supports.
- Never guess the task/profile/model for old records that lack attribution.
- Never change V5.8 retention unless migrations and safety tests prove current limits and crash recovery remain correct.

### 5.5 Read-only query boundary

- All history reads originate in trusted extension contexts (options/popup/background).
- Content scripts and page scripts must not receive arbitrary history queries or full analytics dumps.
- A content script may request sanitized **current action status**, but not browse the user's historical provider usage or price settings.
- Browser messages must not permit `set quota usage`, `delete quota journal`, `download API keys`, `override price and immediately charge`, or any privileged store mutation based on page content.
- Use a typed, allowlisted message API; reject unknown command names and oversized filters.

## 6. Private events and semantic action telemetry

### 6.1 Why minimal UI action events may be needed

A completed correction response proves **a suggestion was produced**, not that the user applied it. To answer the owner's question `How many times did I actually correct something?`, instrument the already-existing **successful editor transaction** rather than assuming Apply succeeded after a click.

### 6.2 Capture only post-commit metadata

Allowed example event fields:

```ts
type AiUiActionKind =
  | 'correction-applied'
  | 'rewrite-applied'
  | 'translation-applied'
  | 'translate-and-rewrite-applied'
  | 'ai-edit-undone'
  | 'preview-copied'; // optional, never interpreted as an applied edit

type AiUiActionEvent = Readonly<{
  id: string;
  operationId: string;
  kind: AiUiActionKind;
  occurredAtMs: number;
  // Never include actual old text, new text, clipboard contents, website URL, API key.
}>;
```

The agent must adapt fields to actual V5.3 event ownership. The `operationId` must be the original opaque operation identity; do not generate new provider requests for analytics.

### 6.3 When an applied event is valid

- The source editor still matches the safe snapshot and transaction succeeds.
- An actual accepted edit is committed to the correct field.
- The action handler receives a positive success signal from the existing editor transaction code.
- The event is stored once with deterministic deduplication (e.g., transaction ID + event kind).
- If storage fails *after* the user edit, **never roll back a valid edit solely to repair analytics**. Show `Statistics may be incomplete`; do not retry the edit.

### 6.4 What must NOT be counted as applied

- Showing a suggestion.
- Copying text to clipboard.
- Clicking Apply while stale-editor check fails.
- Clicking Apply where text is unchanged and existing semantics call that no-op.
- An extension message delivered but not acknowledged as actual editor mutation.
- Four rewrite variants created but none selected.
- Auto-completion of a V5.6 personal shortcut (not an AI application).

### 6.5 Undo semantics

Store a distinct `ai-edit-undone` event **only if** Correctly can conclusively observe a successful undo of a particular AI edit. Native browser `Ctrl+Z` may not be reliably detectable across complex editors; do **not** infer or claim all undos were captured. Dashboard copy must say `Undos recorded by Correctly` rather than `All undos`.

### 6.6 Keep content absolutely out of telemetry

Never persist: selected text, corrected text, rewrite text, translation, personal shorthand expansions, exact page URLs, editor DOM selectors, email addresses, names inside the input, full prompts, API headers, provider raw payload, clipboard data or browsing history.

Even text lengths, hashes and hostnames are **not required** to answer the user's request. Do not collect them speculatively. If a developer proposes them for debugging, reject for V5.9 unless owner explicitly approves a narrow privacy review.

## 7. Analytics schema, storage and aggregation strategy

### 7.1 Recommended design — local IndexedDB projections

Reuse the same extension-origin IndexedDB infrastructure as V5.8, but segregate reporting data via new stores and versioned migrations. Use a new database only if strong repository-specific reasons justify it; two databases make cross-store consistency harder. Retain a thin, typed read-only query service and pure aggregation utilities.

Suggested **illustrative** stores:

| Store | Key | Purpose | May contain private content? |
|---|---|---|---|
| `analyticsDayBuckets` | day + dimension tuple + schema/aggregation revision | Compact historical counts, token fields and priceability status | **NO** |
| `analyticsUiEvents` | unique opaque event ID | Minimal post-Apply/Undo metadata, bounded retention | **NO** |
| `analyticsPrices` | provider/model/rate revision/effectiveFrom | Owner-verified rate history and pricing metadata | **NO keys/text** |
| `analyticsSettings` | single record / version | Display filters, retention, privacy, currency presentation | **NO** |
| `analyticsMigration` | migration ID | Coverage, checkpoints, integrity markers | **NO** |
| `analyticsDailyCoverage` | date / source | Known complete/partial/unknown historical coverage | **NO** |

Consider a materialized **operation facts** store only if the quota journal is aggressively compacted and immutable attribution is otherwise lost. Do not duplicate full operations without need. Better: generate reporting facts at verified settlement with an operation ID and idempotent transaction.

### 7.2 Suggested typed facts

```ts
type AnalyticsTask =
  | 'correction'
  | 'rewrite'
  | 'translation'
  | 'translate-and-rewrite'
  | 'connection-test-generation'
  | 'unknown';

type AnalyticsOutcome =
  | 'success-valid-output'
  | 'sent-http-error'
  | 'sent-timeout'
  | 'sent-network-error'
  | 'sent-invalid-output'
  | 'sent-unknown'
  | 'pending-possibly-sent';

type AnalyticsOperationFact = Readonly<{
  operationId: string;      // never API key or text-derived ID
  attemptAtMs: number;      // dispatch or possibly-sent transition instant
  task: AnalyticsTask;
  providerId: string | 'unknown';
  profileId: string | 'unknown';
  modelId: string | 'unknown';
  outcome: AnalyticsOutcome;
  reportRevision: number;
  tokenUsage: NormalizedTokenUsage;
  rateSnapshotId?: string;  // if a valid, verified snapshot was attached
  schemaVersion: number;
}>;
```

This is *not* the required exact repo shape. Avoid copying an entire optional `analyticsOperationFact` store if the existing quota journal + tested bucket projection already handles idempotency and retention.

### 7.3 Materialization must be idempotent

- Each operation contributes to attempted count **once** at `possibly-sent` commit.
- Settlement modifies its outcome from pending to final **without adding a second attempt**.
- If the same settlement event is delivered twice after worker restart, the second invocation must not change totals.
- If a prior outcome record is modified (e.g., pending→success), subtract/replace its former outcome category exactly once within a transaction, not count both.
- An event that changes billing metadata but not attempt count may update token totals and price coverage exactly once.
- For an old operation processed via migration and then via live callback, enforce unique operation ID/monotonic revision or dedup it.

### 7.4 Transaction boundary options

**Preferred:** while settling a V5.8 operation, atomically write the canonical settlement record and its reporting projection in one IndexedDB `readwrite` transaction *if both belong to the same database and no async provider/network call occurs inside the transaction*.

**Alternative:** immutable canonical V5.8 journal plus a durable local projection outbox/cursor, followed by idempotent replay/reconciliation. This is useful when V5.8 journal ownership must remain unmodified. The viewer should show `Updating statistics...` for lag rather than false zeros.

**Forbidden:** `quota journal commit` then blind untracked `analyticsCounter++` using `chrome.storage.local.set()`; service-worker termination and two-tab races can double count or lose updates.

### 7.5 Aggregate by immutable identity

Daily bucket key must include at least:

- Local calendar **date identity** in a documented timezone (e.g., `Europe/Paris`), not only a formatted string under current locale.
- Exactly one grouping dimension or a uniquely resolved disjoint tuple; avoid combinatorial over-aggregation.
- Provider ID, stable profile ID, exact model ID and task classification where needed.
- Metrics and metadata coverage flags that cannot be mistaken for actual zeros.

Do not store multiple overlapping aggregates and then sum them blindly. Consider one fact-per-operation projection + daily multidimensional buckets from facts; expose a query API that deduplicates the base observations.

### 7.6 Recommended timestamp choice

Count a generation attempt in the period containing its **possibly-sent timestamp**, not its eventual settlement timestamp. Otherwise a request dispatched at 23:59 and answered at 00:01 moves between days and disagrees with V5.8. UI applied events count on **successful Apply timestamp**, which may fall on the next calendar day and is intentionally a different metric.

### 7.7 Integrity requirements

- Counters and event totals must be finite, safe nonnegative integers where they represent counts/tokens.
- No NaN, Infinity, negative counts, invalid timestamps, invalid timezone strings, missing operation IDs or impossible duplicated keys.
- `outcome` must be from a fixed enum, not arbitrary provider message text.
- Never use display labels as stable grouping keys.
- Validate schema at runtime on reads and migration.
- On database corruption, show an explicit banner, block unsafe destructive actions and keep V5.8 quota enforcement fail-closed.

## 8. Calendar periods, date ranges and timezone policy

### 8.1 Reuse V5.8 period identity

V5.8 explicitly specifies:

- `daily`: local calendar day, not a rolling 24-hour interval.
- `weekly`: **ISO calendar week (Monday–Sunday)**, not Sunday-start or rolling seven days.
- `monthly`: calendar month, not rolling 30 days.
- Timezone: one configured valid **IANA timezone** such as `Europe/Paris`.
- Daylight saving time: respect real local midnight boundaries; some days are 23 or 25 hours.

V5.9 should reuse V5.8's tested calendar resolver. Do not make a separate approximate `Date.now() - 7*86400_000` implementation and name it “this week.”

### 8.2 Preset definitions

| Preset | Exact interval in configured timezone | Example when Oct 15, 2026 |
|---|---|---|
| Today | Local midnight today to local midnight tomorrow, exclusive | Oct 15 local calendar day |
| This week | ISO Monday 00:00 to following Monday 00:00, exclusive | Mon Oct 12 through Sun Oct 18 |
| This month | First local day of month to first local day of next month, exclusive | Oct 1–31 |
| Custom | From-date local 00:00 inclusive to day *after* to-date local 00:00 exclusive | Selected dates inclusive in UI |

Important: examples are **calendar fixtures**, not live date calculations to hardcode into the product.

### 8.3 Custom range UX

- Two date inputs (`Start date`, `End date`) with clear labels.
- A custom range is **inclusive by calendar date** in the UI.
- Internally query a half-open instant interval `[startInclusiveMs, endExclusiveMs)` computed using timezone-aware calendar logic, **not `end + 24h`**.
- Reject invalid dates, end preceding start, empty values and unreasonably broad ranges before querying.
- Initial suggested maximum: **366 calendar days**, configurable if actual storage/performance measurements justify more; if limit exceeds retained history, show partial coverage notice.
- An empty range does not automatically select the entire database.
- A custom date range can include days with zero observed events as long as collection coverage was active.
- Current day includes only data observed so far, not inferred future usage.

### 8.4 Timezone change must not secretly rewrite past time

V5.8 settings may let the owner change their quota timezone. Existing bucket identity may be attached to the timezone originally used. Choose and document an explicit analytics policy:

**Recommended:** retain operation UTC timestamps for recent exact history; derive selected reporting timezone on demand for the supported retention horizon. For compact older daily buckets that cannot be reinterpreted without source events, preserve original bucket timezone and show `Historical data grouped using previous timezone`, or mark precise custom regrouping unavailable. Do not silently move, duplicate or drop requests across dates.

Changing the timezone must not reset existing quotas, reassign provider invoices or overwrite a compacted history bucket with guessed event times. Test `Europe/Paris ↔ UTC` and `Europe/Paris ↔ America/New_York`, including DST transitions.

### 8.5 UTC storage vs local presentation

- Store event instants as validated UTC epoch milliseconds.
- Store or derive calendar bucket identity with explicit IANA zone and start/end instant; do not rely on browser locale formatting for bucket keys.
- Group by local calendar date/week/month only at display/query boundaries.
- Display all times with locale-aware format and visible timezone when ambiguous.
- Treat daylight-saving offset transitions and New Year's ISO week 53 correctly.

### 8.6 Cross-midnight and cross-week operations

Example: generation dispatched Sunday 23:59 local and settles Monday 00:02.

- **Attempt:** belongs to Sunday and the prior ISO week.
- **Provider token/cost metadata:** attaches to that same **attempt** and date, even if learned Monday.
- **Edit Apply at 00:03:** a UI action on Monday, reported under Monday in `Applied edits` views; historical link still references the original attempt.
- If the dashboard compares `attempts` and `applies` in one range, explain the different timestamps; counts need not align exactly.

### 8.7 Browser clock tampering and source confidence

- Local statistics reflect extension-recorded timestamps, not an authenticated provider ledger.
- Reuse V5.8 clock-anomaly detection and fail-closed behavior for API requests.
- If clock moved backwards, preserve previous events, mark affected stats as potentially unreliable, and avoid silently merging invalid timestamp windows.
- Do not create a provider call to determine authoritative clock time.

## 9. Accurate metrics: attempted, completed, corrected, applied, undone

### 9.1 Core counts and their formulae

For filtered operation facts `F` (unique `operationId`, possibly sent, attempt timestamp in requested range):

```text
attempts                = count(F)
successful_operations   = count(F where final normalized outcome = success-valid-output)
correction_checks       = count(success-valid-output AND task=correction)
rewrites_generated      = count(success-valid-output AND task=rewrite)
translations_generated  = count(success-valid-output AND task=translation)
combined_generated      = count(success-valid-output AND task=translate-and-rewrite)
connection_tests        = count(task=connection-test-generation, sent)
failed_or_unknown       = count(F where final outcome != success-valid-output)
```

The `failed_or_unknown` summary must be divisible by pending, provider-error, validation-error and unknown outcome if actual metadata supports that distinction. Do not treat a success with unchanged correction as an error.

### 9.2 More precise correction metrics

If the validated correction response contains safe structured metadata indicating `hasErrors` or an equivalent trustworthy flag, the agent may add:

- `Checks with errors detected` (AI reported possible errors).
- `Checks with no errors detected` (AI reported no correction needed).
- `Changes applied` (source editor actually updated).

Do not infer `hasErrors` merely by comparing normalized whitespace in a way that overrides existing V5.2 semantics; use its tested typed result. The model can be wrong: label as **AI-reported**, not an objective language correctness guarantee.

### 9.3 Gross and net applications

Preferred widgets:

- **Applied AI edits (gross)** = number of uniquely confirmed Apply transactions.
- **Recorded Correctly undos** = number of uniquely confirmed matching Undo transactions.
- **Net AI edits retained** = only if there is a fully reliable link and defined subtraction semantics; otherwise **omit**. Avoid deriving a `net` metric from incomplete native Ctrl+Z observation.

Undo never reduces attempts or token estimates, and it must not delete previous application events.

### 9.4 Rewrites and candidates

- `rewrite_requests` counts sent attempts of task `rewrite`.
- `rewrites_generated` counts successful rewrite operations.
- `rewrite_variants_shown` is optional and requires validated response cardinality persisted as a small number; never infer from requested count.
- `rewrites_applied` counts actual chosen replacements.
- No `per-style API call` multiplication for shared generation.
- If a single operation's output is copied twice, two clipboard actions may exist, but still one model attempt and zero applied edits.

### 9.5 Translation task taxonomy

Respect V5.8 canonical task names:

```text
correction
rewrite
translation
translate-and-rewrite
connection-test-generation
```

The dashboard can use friendly localized labels, but do not rewrite persisted task IDs. Display `Connection tests` separately so a model test does not masquerade as a correction. If V5.7's key check uses a metadata-only endpoint, it is not counted as a generation attempt by V5.8.

### 9.6 Success and failure when the provider replied but parsing failed

- Sent provider reply that fails response schema or semantic validation: **one attempt**, not a successful correction/rewrite/translation.
- Provider HTTP 429: **one possibly-sent attempt** according to the V5.8 conservative request rule, unless the V5.8 record definitively established it never dispatched. Billing unknown, not assumed positive or zero.
- Local cap-denied request: **zero new sent attempts**.
- Retry explicitly initiated after ambiguity: new attempt ID, counted separately.

### 9.7 Optional blocked-actions metric

If the owner values it, show `Locally blocked by limits` as a **separate, non-billable diagnostic**, never counted as `requests used`. Do not create persistent detailed per-tab denial logs. Prefer a simple period aggregate and avoid potential confusion with provider 429. This metric is optional for V5.9 unless reliable source data already exists.

### 9.8 Reconcile to V5.8 current-window totals

For period compatible with the quota policy and complete history:

- Statistics `Requests used` for **global/current window** should equal V5.8 `global counted`, with reservations displayed separately as `In progress`.
- Historical synthetic migration where old aggregates are incomplete should display explicit caveat rather than pretending equality across missing periods.
- If an actual same-window discrepancy appears, do not change quota counts to match analytics. Show an integrity warning, record safe diagnostics (counts and IDs, not text), and run repair/rebuild from canonical journal where safe.

## 10. Provider token usage normalization and missing metadata

### 10.1 Source of token truth

Gemini and OpenAI adapters introduced by V5.7 should return normalized usage metadata. V5.9 **consumes these adapter outputs**. It must not parse arbitrary content scripts or raw provider JSON in UI components.

Inspect the actual provider endpoint and SDK/REST transport before implementing normalization. Provider field names and token categories vary by model and API version. Reference examples below require verification against the current **official provider documentation**.

### 10.2 Minimum normalized token contract

```ts
type TokenCoverage =
  | 'complete-for-known-components'
  | 'partial'
  | 'missing'
  | 'invalid';

type NormalizedTokenUsage = Readonly<{
  coverage: TokenCoverage;
  source: 'provider-reported' | 'legacy-unknown';
  inputTokens?: number;          // safe nonnegative integer; not defaulted to 0
  outputTokens?: number;
  totalTokens?: number;
  reasoningTokens?: number;      // often a subset of output/billable categories
  cachedInputTokens?: number;    // often a subset of input, NOT automatically additive
  otherBillableTokens?: number;  // only if verified disjoint and priced explicitly
  providerRawCategoriesKnown?: boolean;
}>;
```

If the current V5.8 shape differs, create a documented compatibility adapter. Do **not** change quota decisions based on token fields.

### 10.3 Parsing rules

- Accept only finite, safe, nonnegative integers.
- `0` is valid **when explicitly reported**.
- Missing `inputTokens` is **unknown**, not zero.
- A reported `totalTokens` alone is insufficient to split cost between differently priced input and output.
- Do not sum `inputTokens + cachedInputTokens` if cached is a **subset** of input.
- Do not sum `outputTokens + reasoningTokens` if reasoning is already included in output.
- Do not use `totalTokens` to invent missing input/output splits.
- Keep provider-reported raw category names out of permanent storage unless needed as bounded, validated enums for pricing; do not store full response objects.
- If metadata is inconsistent (e.g., negative, unreasonable totals, category mismatch), mark `invalid`, preserve safe aggregate state and report missing price confidence.

### 10.4 Gemini adapter considerations

Relevant Gemini generation responses can include `usageMetadata` with fields such as input/prompt, candidate/output and thinking-token categories depending on model, endpoint and response structure. The agent must verify the real response path, how thinking and cached input are included, and whether model pricing differentiates categories. **Never assume all models return all categories or bill identically.**

### 10.5 OpenAI adapter considerations

Relevant OpenAI generation responses can include a `usage` object with input/output totals and sometimes cached-input or reasoning-output details depending on endpoint/model. The agent must confirm whether using Responses API or another supported surface and how nested fields relate to headline totals. **Do not double count subset details.**

### 10.6 Metadata absent due to timeout

For a possibly-sent request that timed out with no response:

```text
Attempt count:            1
Input tokens reported:    Unknown
Output tokens reported:   Unknown
Estimated cost:          Unknown / unpriced attempt
Billable by provider:     Unknown
```

UI should show `1 attempt without complete token metadata`. **Do not estimate cost from character length** unless owner explicitly approves and the result is unmistakably labeled speculative; V5.9 default is **not to guess**.

### 10.7 Aggregation with incomplete observations

Suppose three operations:

- A: input 100, output 50 (fully reported).
- B: input 250, output 25 (fully reported).
- C: no usage metadata after timeout.

Then show:

```text
Requests:                     3
Reported input tokens:      350 (2/3 attempts with data)
Reported output tokens:      75 (2/3 attempts with data)
Token coverage:             Partial: 1 attempt unknown
Estimated cost:             Partial estimate (if A/B priceable)
```

Do not show `Total tokens: 425` without the qualifier `reported`/`partial`, because that misrepresents C.

### 10.8 Token calculation presentation

- For all-total aggregations where input/output coverage is complete, input + output may be shown alongside provider total **only if documented component definitions are compatible**.
- If the provider's `totalTokens` includes an extra non-displayed category, show provider reported total as a separate fact rather than force arithmetic equality.
- Do not claim token total = billing total.
- Token counters never replace V5.8 request caps.

## 11. Estimated cost: price registry and calculation engine

### 11.1 First principle: estimated, not actual

The extension should compute a **local estimate of model generation cost**, not the user's confirmed Google/OpenAI invoice. Real charges may depend on price tier, token category, cached input, provider promotions, batch rates, taxes, currency conversion, model/region, tools, tiered rates or revisions to billing logic. As the project is personal/frontend-only, the dashboard should not pretend to fetch authoritative invoice data.

### 11.2 Zero-cost cases versus unknown-cost cases

- **No sent attempts in selected period:** estimated model-generation cost may truthfully show `$0.00`.
- **Local cap denial, before provider dispatch:** no generation cost for that denied action.
- **Sent request with complete tokens and verified rate:** numeric **estimated cost**.
- **Sent request with token metadata but unknown model price:** **Unknown price**, not `$0.00`.
- **Sent request missing usage metadata:** **Unknown token usage**, not `$0.00`.
- **Sent request whose provider returned HTTP error:** charge **unknown unless documented proof establishes otherwise**.
- **Legacy attempt without precise timestamp/model/pricing:** `Unpriced legacy history`.

### 11.3 Pricing reference model

Do not hard-code current prices into source constants without source date, effective period and owner visibility. Use a versioned local **pricing registry** keyed to exact provider/model and usage category:

```ts
type PriceSource = 'official-manually-verified' | 'owner-entered';
type PriceEntry = Readonly<{
  id: string;                // immutable UUID / deterministic version ID
  providerId: string;
  exactModelId: string;      // provider-native ID, never guessed alias
  currency: 'USD';
  unit: 'per-million-tokens';
  inputUsdPerMillion: string;   // decimal strings, not fragile JS float config
  outputUsdPerMillion: string;
  cachedInputUsdPerMillion?: string;
  // Only add separate reasoning/other rates if official policy actually needs them.
  effectiveFromMs: number;
  effectiveToMs?: number;
  sourceKind: PriceSource;
  sourceUrl?: string;
  verifiedAtMs: number;
  notes?: string;            // bounded; no user text
  pricingRuleVersion: number;
}>;
```

**Implementation note:** model names change. Pricing aliases are allowed *only* if documented as official price-equivalent groupings, with tested mapping and a visible source; unknown IDs must remain unpriced.

### 11.4 Where pricing entries come from

Two acceptable approaches, with no hidden network activity:

**A. Curated entries checked against official pricing pages during development.** Ship with a clear `last verified` date, URLs and exact model applicability; show that rates may be stale. These are examples/reference data, **not a promise of future prices**.

**B. Owner-maintained custom prices in settings.** Provide an editor with explicit USD/1M input/output rates, optional cached input rate, exact model and effective date, source label. Validate all values before Save. Never send the pricing form to a provider.

**Preferred:** support A + optional B override, where user override is clearly labeled and scoped. If implementation time is limited, build a correct B with optional confirmed defaults rather than a false 'live pricing' integration.

### 11.5 Cost calculation formula, simple two-rate case

For an attempt with known, billable-compatible input/output token components, rate reference and no special categories:

\[
\text{estimated USD} = \frac{\text{inputTokens}\cdot\text{inputUSDperMillion} + \text{outputTokens}\cdot\text{outputUSDperMillion}}{1{,}000{,}000}
\]

**Example ONLY**, using hypothetical rates of `$0.10 / 1M input` and `$0.40 / 1M output`:

```text
Input = 1,000 tokens
Output = 200 tokens
Input estimate = 1,000 × $0.10 / 1,000,000 = $0.00010
Output estimate = 200 × $0.40 / 1,000,000 = $0.00008
Total estimate = $0.00018
```

These rates are **illustrative numbers**, not a current official Gemini or OpenAI price assertion. Do not silently show them as a current live price in production.

### 11.6 Avoid premature rounding

- Do all accumulation in a sufficiently precise numeric representation: an exact decimal library already approved in the repository, or well-tested scaled integers/BigInt with documented units and overflow checks.
- Convert official price decimal strings using a strict parser (reject exponent tricks if not supported; reject NaN, infinity, negatives, locale commas unless deliberately normalized).
- Multiply and sum at adequate precision; **round only at display/export boundary**.
- Small results under one cent should display `< $0.01` or `$0.00018` (depending selected precision), **not** falsely imply exact zero.
- A rounded table sum can differ by a cent from sum of row display values. Document rounding and use aggregate unrounded calculations before formatting.
- Never convert USD to EUR using a guessed exchange rate. Optional EUR view requires a documented, timestamped FX source or manual user-provided rate and clear estimated label; **defer EUR conversion by default**.

### 11.7 Cached input and reasoning categories

Do not use one simplistic formula for models whose documented billing requires separate categories:

- If cached input is a **subset** of total input, price `uncachedInput = inputTotal - cachedInput`; add `cachedInput × cachedRate`, validating nonnegative difference.
- If reasoning output is already included in output and priced at the same output rate, do not add it twice.
- If provider bills reasoning tokens separately or the category's inclusion is uncertain, require a verified model-specific pricing rule or mark cost **partial/unknown**.
- If an API feature returns tool/audio/image usage that the registry cannot price, mark **partial**; do not hide charges behind the text token estimate.
- For multi-tier context-length pricing, a single flat rate is insufficient; support a verified rule variant or display `Cannot estimate for this pricing tier`.

### 11.8 Price effective date and historical attribution

- Determine applicable price using **attempt dispatch timestamp**, exact provider model ID and relevant pricing-rule version.
- A later price update should **not silently rewrite historical observations**. Choose one clear reporting policy:
  - **Recommended:** store immutable `priceSnapshotId` when a verified rate is available at dispatch/settlement; historical estimate uses that snapshot.
  - For previously unpriced history, the owner may deliberately choose `Re-estimate using selected reference price` with an explicit disclaimer; keep original `unknown at request time` provenance.
- Editing an existing price entry must create a **new version**, not mutate previous historical rate silently.
- If old history lacks exact model ID or effective rate evidence, mark unpriced; do not choose today's price retroactively without a labeled re-estimation mode.

### 11.9 Price and token completeness states

Suggested UI states for selected period:

| State | When | Display |
|---|---|---|
| Complete estimate for known pricing | Every possibly-sent observation fully priceable under supported billing rules | `Estimated: $X.XXXX` + disclaimer |
| Partial estimate | Some operations priceable, others lack prices/tokens | `At least $X.XXXX estimated from M of N requests; remaining cost unknown` |
| Unknown estimate | Attempts exist but none priceable | `Estimated cost unavailable` |
| Zero observed requests | No counted attempts and storage/coverage trustworthy | `Estimated cost: $0.00` |
| Historical coverage incomplete | Old history missing | Banner explaining earliest reliable date; numeric result scoped to covered data only |

**Phrase carefully:** `At least` is a lower bound on the **computed subset**, not necessarily a certified lower bound on actual invoices (discounts/credits may lower billed total). Safer default: `Partial modeled estimate: $X for M/N attempts; others unknown`.

### 11.10 Prevent pricing from becoming a security bypass

- No price editor can modify V5.8 counted attempts, quota policy or permit state.
- Changing displayed prices cannot enable a blocked request.
- No automatic provider billing endpoint calls when entering the dashboard.
- No custom JavaScript `pricing formula` entered by the owner; use typed, validated rule variants.
- Pricing URLs are treated as **untrusted labels**, validated to approved `https:` references if clickable; never fetch arbitrary URLs based on imported data.

### 11.11 Error messages for cost estimation

Examples:

- `Gemini: token usage not returned for 2 requests. Estimated cost is incomplete.`
- `Unknown model price for openai/<exact-model-id>. Add a price reference to estimate these tokens.`
- `The displayed value is a local estimate, not your provider invoice.`
- `Pricing reference last verified on [date]; check your provider's current rates.`
- `This history predates token tracking. Earlier costs cannot be reconstructed exactly.`

Never show `Free` merely because the model ID could not be mapped.

## 14. Filters, comparison, refreshing and service-worker lifecycle

### 14.1 Query path

```text
Trusted options/popup
  -> input validation (period, date range, dimensions, page, sort)
  -> read-only analytics query service
  -> IndexedDB indexed reads or bucket projection
  -> pure grouping/price coverage calculations
  -> localized presentation
```

Avoid recalculating the full history on every keystroke in the settings UI. Use memoization of immutable query results only if invalidation after a new operation is reliable.

### 14.2 Refresh semantics

- Refresh must never call Gemini/OpenAI.
- Refresh while a generation is pending may show a `Pending` operation or later success without double counting.
- Concurrent refreshes should not create duplicate rows.
- If background worker suspended/restarted, the UI must reconnect/requery using durable storage, not rely on a RAM-global metrics cache.
- Browser storage changes or a revision notification can trigger refresh, but notifications must be narrowly scoped and throttled.

### 14.3 Interleaving settings changes

- If user renames a profile, use current display name but historical immutable profile ID.
- If user deletes an API key, keep historical aggregate attribution without the key value.
- If user changes a model route, past operations retain their original model ID.
- If user changes pricing while dashboard open, recompute **only** where chosen price policy permits, with clear snapshot/version status.
- If user changes quota timezone, analytics handling must follow documented timezone policy (section 8), not silently reset.

### 14.4 Multi-tab dashboard consistency

- Two options tabs may filter separately; filtering is local UI state.
- No options tab may directly mutate V5.8 enforcement stores.
- A new generation from a third website tab must appear once in both dashboards after refresh or a safe revision notification.
- A storage migration in one tab must coordinate DB `versionchange`/`blocked` handling with the other; old connections must close cleanly.

### 14.5 Browser worker behavior

Chrome MV3 service workers can be suspended; do not depend on worker global counters or timed callbacks for statistics correctness. Make DB calls short and scoped. Do not hold a transaction open while fetching network data, rendering a chart, awaiting clipboard access or waiting for UI interaction. Register worker listeners in the supported top-level pattern.

## 15. Retention, migration, historical backfill and partial coverage

### 15.1 Retention policy must be explicit and editable only where safe

Recommended default for local analytics:

- **Daily aggregate history:** keep at least **12 months** or a documented configurable period; 365/366-day boundaries validated.
- **Recent operation-level metadata:** bounded period such as **90 days**, **only** if full historical breakdowns are preserved in trustworthy daily buckets and V5.8 quota/recovery records are no longer needed.
- **Unresolved/possibly-sent operation records:** V5.8 retains/reconciles them per safety policy, regardless of dashboard history settings.
- **UI Apply/Undo events:** compact to daily counters after safe reconciliation, unless a longer exact custom-date requirement needs metadata.
- **Pricing reference history:** preserve all versions required to explain existing estimated-cost snapshots; cleanup must not render retained history inexplicably unpriced.

The numbers are product defaults to validate in performance tests; do not impose a hard 90-day operation deletion when it violates V5.8's current monthly limit/recovery horizon.

### 15.2 Make gaps visible

- The existing V5.8 plan might have aggregate counts but not detailed per-day provider token history before V5.9.
- On upgrade, import what is **verifiably stored**.
- If a historical date only has total requests without tasks/tokens, display the request count under `Legacy / unknown attribution` and mark token/cost coverage unknown.
- If a prior count only existed as a monthly total, do not invent a daily distribution or allocate uniformly over days.
- Show `Statistics fully tracked since [date]` with `Earlier usage may be incomplete` whenever appropriate.

### 15.3 Migration algorithm

1. Read current schema/revision and migration history.
2. Snapshot essential metadata counts and checksums **without copying keys into reports**.
3. Build a deterministic migration plan based on actual old records and supported transformations.
4. Apply schema changes transactionally as far as IndexedDB permits; do not run network calls in migrations.
5. Track a versioned, idempotent migration marker and verified projection revision.
6. Reconcile current V5.8 quotas before and after.
7. Recompute reporting materializations from canonical data if safe.
8. Mark unresolvable historical coverage gaps rather than invent information.
9. Keep old credentials, routes, shortcuts and limits unchanged.
10. Test migration replay/interruption, duplicate old IDs and invalid legacy rows.

### 15.4 Existing counts before tracking started

If earlier versions stored only `count used this month` and not individual timestamps, the only honest display is e.g. `Legacy monthly requests: 120; daily distribution unavailable`. They cannot be attributed to an exact date or provider without evidence. Add separate summary, not false dated bars.

### 15.5 Compaction algorithm safety

- Acquire safe ownership of analytics compaction (e.g., versioned transaction, small bounded work); do not introduce a blocking global timer.
- Verify day buckets include all finalized event contributions before deleting optional detailed reporting facts.
- **Never** prune V5.8 unresolved or active-window records only because V5.9 retention threshold expired.
- Protect against duplicate compaction after worker restarts with idempotent markers.
- Delete old analytics metadata only after checksum/reconciliation passes; otherwise stop and show recoverable warning.

### 15.6 Import/export asymmetry

Export is required for safe stats. **Importing historical analytics is optional and risky**; do not implement general import unless the owner explicitly requests it in a later milestone. Arbitrary imported operations must **never** be allowed to impersonate actual V5.8 attempts or adjust quotas.

## 16. Export, delete, privacy and security behavior

### 16.1 Export purpose

The owner should be able to save a copy of the **aggregated local statistics** for their own analysis, without exposing their API keys or what they typed.

### 16.2 Recommended formats

- **CSV** for selected period and grouping (Excel/LibreOffice friendly), with UTF-8 BOM only if needed after real spreadsheet compatibility test.
- **JSON** containing version, selected period/timezone, generation timestamp, metric definitions, rows, price provenance and coverage information.
- Both formats must contain the *same underlying numeric facts* as the displayed table before rounding.

### 16.3 Recommended export JSON outline

```json
{
  "schemaVersion": 1,
  "exportType": "correctly-statistics-aggregates",
  "generatedAt": "2026-10-15T10:00:00.000Z",
  "timezone": "Europe/Paris",
  "range": {"startDate": "2026-10-01", "endDate": "2026-10-15"},
  "currency": "USD",
  "costKind": "estimated-not-invoice",
  "coverage": {"complete": false, "note": "example-only"},
  "rows": []
}
```

**Illustration only:** The timestamp is a static example and should be populated from actual runtime data. Do not export it as a real observed event.

### 16.4 CSV injection protection

CSV cells that begin with `=`, `+`, `-`, `@`, or other spreadsheet formula-triggering characters can be interpreted as formulas. A malicious or badly formatted model/profile label must be sanitized or formula-escaped in exported CSV, in addition to normal CSV quote escaping. Test with injected labels including `=HYPERLINK(...)`, line breaks, tabs and leading whitespace before `=`. Do not include executable formulas in the output.

### 16.5 Export allowlist

Export **only** approved fields:

- Aggregate dates, task/provider/model sanitized names or stable non-secret IDs.
- Counts, reported token totals, completeness indicators.
- Estimated numeric USD amounts with source and rule versions.
- No raw provider API responses.
- No raw/suffix of API key (the profile stable ID is not a secret but may be omitted by default).
- No selected text, generated text, clipboard content, shortcut dictionary, domain URLs, email addresses from prompts, error body strings or browser history.

### 16.6 Confirmation before deletion

A `Delete statistics history` feature must:

1. Clearly say **what** is deleted (`analytics history and reporting projections`) and **what is NOT** deleted (`API credentials, quota policies and active quota counting`).
2. Require explicit user confirmation with a destructive-action prompt.
3. Refuse unsafe deletion when active V5.8 counters or pending operations would become inconsistent.
4. Use a transaction/migration-safe approach that can rebuild current required analytics aggregates from preserved V5.8 source records where necessary.
5. Not claim to delete provider-side data, invoices or Google/OpenAI account records.
6. Explain that browser-profile resets/uninstalls can erase local stats; exports are backups, not cloud sync.

If the source data needed for quota and history cannot be cleanly separated, **do not expose deletion** until a safe implementation is proven; offer read-only export + retention settings and document the blocker. A fake `Reset all` button is unacceptable.

### 16.6.1 Special case: deleting analytics while V5.8 source records remain

A naive implementation of `Delete statistics history` could delete analytics buckets, then recreate the exact same historical entries on the next reconciliation pass by rereading intact V5.8 operations. **This is an important privacy/deletion correctness issue.** If deletion is implemented:

- Record a small, durable **analytics deletion watermark / exclusion policy** for the deleted time range, separate from V5.8 quota stores. Do not store the deleted content in the watermark.
- A replay/backfill worker must obey this exclusion policy and **not regenerate deleted reporting history** from preserved enforcement records.
- Preserve current V5.8 counters and unresolved operations even when the user requests deletion. The Usage Limits page must still show their true usage. If current-window summaries necessarily reveal request counts, explain that required quota data cannot be erased without losing cap protection; never show an inconsistent `0 attempts` next to `cap 5/5 used` without a `Statistics history deleted; quota usage preserved` disclosure.
- New attempts after deletion are recorded normally using new operation IDs. Specify whether deleting a range is inclusive of deletion timestamp and avoid reintroducing a partially deleted event through late settlement.
- When the V5.8 journal finally becomes safe to prune, analytics deletion watermark retention can be reduced according to verified source/retention boundaries.
- If this interaction cannot be implemented and proven safe, **do not ship a Delete button** in V5.9. Documentation should explain why deletion was deferred, rather than pretending cache clearing is historical deletion.

**Mandatory additional tests:** delete old history, force projection reconciliation, restart worker, re-run migration, confirm deleted historical details do not reappear; verify quota is still enforced and new post-deletion events are recorded correctly.

### 16.7 Credential protection and storage access levels

V5.7 identified a crucial Chrome behavior: `chrome.storage.local` can be exposed to extension content scripts by default. Preserve V5.7's tested trusted-context access restriction or equivalent secret isolation. Do not accidentally weaken this by adding statistics UI content scripts that require reading `chrome.storage.local` secrets.

- API keys should be accessible only to trusted options/background logic that needs them, not to website code.
- Statistics query responses should carry only safe aggregated metadata.
- Content scripts must not call unrestricted `getAllStats()` and receive the complete history.
- Redact sensitive values in error logs, screenshots and test reports.
- Do not embed keys or billing identifiers in export filenames.

### 16.8 Threat model for a personal browser extension

Protection is pragmatic, **not perfect cryptographic security against a compromised browser, malicious local process or owner-controlled extension developer tools**. Document the limitations. Do not promise provider invoice protections from local data access restrictions.

### 16.9 Data deletion versus quota reset

**Critical invariant:** Deleting **analytics** does not alter `quotaCounters`, `quotaPolicy`, reservations, active operation journal needed for V5.8 recovery, or alert thresholds. Local billing-request limits must remain enforced for the rest of the applicable day/week/month. Tests must prove this with limit=1 and several tabs.

## 17. Performance, concurrency, accessibility, localization

### 17.1 Performance requirements

- No per-keystroke analytics persistence or API requests; the feature works after explicit AI operations only.
- Summary load must not perform unbounded full journal scan across all history on every render.
- Use IndexedDB indexes and daily reporting materializations for month/year selection.
- Cache read-only projections by version/revision only when safe to invalidate.
- Measure performance (p50/p95 load time, query count, memory usage) using synthetic 1k/10k/100k operation fixtures; record actual numbers rather than inventing fixed promises.
- Keep chart data bounded/resampled to readable daily/week bins; **do not average or fabricate missing data**.
- CSV export should stream or chunk when large enough to avoid blocking UI, and must be cancellable without corrupting storage.

### 17.2 Concurrency requirements

- Two workers/options windows settling the same operation: no double count.
- Analytics read while operation settles: at worst consistent snapshot or explicit updating state, not impossible negative outcomes.
- One options page editing a price reference while another queries it: persisted revision isolation and clear conflict handling.
- Concurrent export and new request: export documents snapshot timestamp/revision; totals should be internally coherent.
- Worker suspend during an analytics projection must resume idempotently.

### 17.3 Accessibility requirements

- All controls keyboard-operable; correct focus order and visible focus ring.
- Date picker usable without pointer; errors announce via accessible status text.
- Charts have accessible data tables, meaningful titles and categories.
- Color is never the only indicator of missing data, failed operation or cost coverage.
- Status updates announce appropriately without stealing focus from input fields.
- Buttons have specific text (`Export CSV`, `Export JSON`, `Delete local statistics`) rather than ambiguous icons alone.
- Support zoom/text scaling, reduced motion and narrow windows.
- Dropdowns provide clear labels for provider/model/task/date filters.

### 17.4 Locale formatting

- FR/EN user-facing strings follow existing extension locale setting.
- Preserve internal stable task/provider ID strings.
- Format dates using `Intl.DateTimeFormat` with configured timezone, not implicit device locale alone.
- Format numbers with `Intl.NumberFormat` and units, with consistent decimal rounding for cost.
- `$0.00018` in English and locale-appropriate decimal in French, still **USD**.
- Do not silently convert USD to EUR using an unverified rate.

### 17.5 Visual regressions

- Statistics must not block content-script triggers or right-click menus.
- Opening options must not steal editor focus from a website unless user explicitly activates options.
- New chart/CSS dependencies must be bundled locally, Manifest V3 CSP compatible, license-checked and tree-shaken where possible; do not inject remote scripts.
- Do not upgrade a major UI framework without necessity.

## 18. Failure modes and incident handling

### 18.1 Classify failures before fixing

| Failure class | Representative symptom | Correct response |
|---|---|---|
| Storage unavailable | Dashboard cannot open IndexedDB | Show `Statistics temporarily unavailable`; **never** reset quota counts |
| Schema mismatch | Old profile migration fails | Stop migration, preserve data, produce safe diagnostics |
| Missing token usage | Timeout or provider omits usage | Show `Unknown`, not `$0.00` |
| Invalid price | Negative or malformed USD rate | Reject price entry; keep last valid version |
| New model ID | Price not in registry | `Unpriced model` with configuration link |
| Concurrency | Duplicate settlement counted twice | Idempotent operation fact/bucket projection |
| DST boundary | Requests appear on wrong day | Shared V5.8 calendar resolver + fixture test |
| Deleted profile | History disappears | Keep attribution under stable deleted-profile placeholder |
| Stale editor | Apply clicked but no edit | Do not increment applied count |
| Local limit reached | Dashboard shows another request? | Blocked request must not count as sent; reconcile read-only projection |
| History partially compacted | Custom date range lacks details | Partial coverage and limitations message |
| Security | Export includes a key or text | Treat as release blocker, sanitize allowlist, add regression |
| UI perf | Monthly chart takes excessive time | Index/buckets, bounded rendering, profile benchmarks |
| Price drift | Old prices changed silently | Immutable price versioning + snapshot provenance |
| CSV formula injection | Exported cell executes formula | Escape untrusted formula-leading fields |

### 18.2 Repair principle

When analytics disagrees with V5.8 quota data, **never “repair” it by zeroing V5.8 counters**. Determine authoritative source; rebuild analytics projections from canonical facts or mark coverage uncertain. Preserve keys and request caps.

### 18.3 Recovering from interrupted IndexedDB migration

- Open database in read/diagnostic mode if possible.
- Inspect version/migration marker, indexes and observed counts.
- Re-run only idempotent steps; do not import the same old record twice.
- Handle `blocked`/`versionchange` by closing stale connections and prompting stale options tabs to reload.
- If rollback impossible without data loss, halt with exact no-secrets recovery instructions rather than guessing.

### 18.4 API or pricing data is not an analytics availability dependency

Statistics must remain viewable **offline**, assuming local IndexedDB is accessible. Viewing history cannot require an active Gemini/OpenAI key or network connection. Price references are local; no remote fetch in standard dashboard render.

## 20. Unit, integration and invariant test plan

### 20.1 Test philosophy

The owner specifically wants to minimize time spent discovering bugs after the coding agent finishes. Accordingly, testing must be **deterministic, adversarial, automated where feasible, and documented**. Do not merely create a list of test titles; implement executable fixtures and assert exact state and outputs.

Tests should run with **fake APIs**, **fake clock**, isolated **IndexedDB test database**, and browser extension test profile. Never use real paid provider requests for the routine suite.

### 20.2 Minimum test layers

**Layer 1 — Pure functions:** date resolver, data validation, grouping, price calculation, labels, formatting, coverage classification.

**Layer 2 — Storage/transactions:** schema upgrade, idempotent materialization, concurrency, duplicate settlement, truncation, migration, compaction, corruption.

**Layer 3 — End-to-end extension boundaries:** V5.8 permission/dispatcher, provider adapter normalized usage, trusted UI events, options query, export.

**Layer 4 — Real-browser manual:** Chrome and Brave context menu/keyboard/preview/Apply/statistics, offline modes and worker lifecycle.

### 20.3 Hard invariants to assert in automation

- **INV-01:** Every possibly-sent V5.8 operation contributes once to requests used.

## 22. Troubleshooting: symptom, root cause, repair, retest

### T01 — Requests used doubles after settlement

**Symptoms:** One correction appears as two attempts.  
**Likely cause:** attempt counted on possibly-sent commit and again on completed status.  
**Repair:** idempotent projection by unique operation ID; state transition updates outcome without incrementing attempt.  
**Retest:** deliver duplicate settle events 10 times and compare against one V5.8 ledger ID.

### T02 — Four rewrite tones show as four requests

**Cause:** counting returned candidate list as API attempts.  
**Repair:** count one provider generation request; candidate count is separate optional metric.  
**Retest:** exactly one fetch, one attempt and four candidate variants.

### T03 — Statistics show $0.00 after a timeout

**Cause:** missing usage treated as zero.  
**Repair:** explicit token coverage and `cost unavailable/partial`.  
**Retest:** network timeout with possibly-sent committed state.

### T04 — Token totals are too high with cached input

**Cause:** cached-input subset added on top of total input.  
**Repair:** compute disjoint uncached/cached subsets under verified provider rule.  
**Retest:** N-03 fixture and adapter raw response fixture.

### T05 — Cost changes when selecting another model

**Cause:** pricing applied from current active route rather than operation's original frozen model.  
**Repair:** use immutable model ID and historical rate snapshot.  
**Retest:** switch Gemini→OpenAI after first request; history stays attributed to original.

### T06 — Applying a stale preview increments edits

**Cause:** Apply click counted before editor transaction succeeds.  
**Repair:** observe confirmed successful transaction only.  
**Retest:** change source field before Apply; stats unchanged.

### T07 — Clicking Copy increments applied rewrites

**Cause:** shared Copy/Apply callback sends same analytics event.  
**Repair:** separate event kinds and only successful text mutation counts.  
**Retest:** copy a candidate three times, Apply zero.

### T08 — Deleting statistics resets daily cap

**Cause:** destructive operation deleted shared `quotaCounters`/operation journal.  
**Repair:** isolate analytics deletion from V5.8 stores; preserve active ledger and cap verification.  
**Retest:** cap=1, send=1, delete history, second send still denied.

### T09 — Monday weekly count is off by one day

**Cause:** Sunday-start or rolling seven-day logic.  
**Repair:** reuse shared ISO week timezone resolver.  
**Retest:** events at Sun 23:59 and Mon 00:00 for Europe/Paris.

### T10 — March/October DST gives an empty or duplicate day

**Cause:** adding 86,400,000 ms to represent local day.  
**Repair:** timezone-aware calendar arithmetic.  
**Retest:** Paris 23h/25h DST fixtures.

### T11 — No historical data before upgrade

**Cause:** V5.8 compacted old operations or stored only aggregate counters.  
**Repair:** import exactly supported legacy counts, mark missing detail/coverage.  
**Retest:** migration fixture with monthly-only legacy count; no fake daily rows.

### T12 — A deleted API key removes its prior rows

**Cause:** joining analytics history only to currently existing profile list.  
**Repair:** stable historical profile identity with safe deleted-profile label.  
**Retest:** delete profile, reopen page, totals unchanged.

### T13 — UI freezes when selecting a year

**Cause:** unindexed full journal scan/repeated chart rendering.  
**Repair:** materialized day buckets, indexes, bounded aggregation, pagination.  
**Retest:** 100k synthetic observations, record actual timings.

### T14 — Same day shows different counts in charts and export

**Cause:** different grouping implementations, rounding or filter rules.  
**Repair:** one canonical query result and shared pure aggregation; format only at presentation.  
**Retest:** compare structured chart data, table rows and CSV/JSON totals.

### T15 — Spreadsheet opens an exported formula

**Cause:** CSV injection through untrusted model/profile label.  
**Repair:** formula-safe cell escaping plus RFC-style CSV quoting.  
**Retest:** formula-prefixed cells in spreadsheet import fixture.

### T16 — Statistics page causes paid requests

**Cause:** provider key validation/usage fetch on page mount.  
**Repair:** remove network effects; use only local IndexedDB reads.  
**Retest:** fake provider spy stays at zero across page mount/filter/export.

### T17 — A newer price revision overwrites old history

**Cause:** mutable shared rate row used retroactively.  
**Repair:** price snapshots / effectiveFrom / price rule version and explicit re-estimation mode.  
**Retest:** price revision while existing history visible; old snapshot stable.

### T18 — Statistics show negative counts

**Cause:** duplicate decrement on pending→completed or UI event undo.  
**Repair:** idempotent projection and transaction invariant validation.  
**Retest:** repeated finalize/rollback with injected transaction failure.

### T19 — Quota limits stop working after adding indexes

**Cause:** IndexedDB schema migration deleted or changed V5.8 stores, blocked upgrade, or shared readwrite locking mistake.  
**Repair:** non-destructive upgrade preserving original keys and transactions; close stale connections.  
**Retest:** V5.8 full cap tests plus V5.9 storage migration and crash tests.

### T20 — Two browsers/tabs have different statistics

**Cause:** Chrome and Brave profiles have separate local storage; or within one browser two tabs have stale caches.  
**Repair:** explain **per-browser-profile** isolation; for same profile subscribe to revision and refresh safely.  
**Retest:** two options tabs in same profile reconcile; Chrome vs Brave correctly independent unless explicitly exported.

### T21 — Analytics records secret prompt or API key

**Cause:** logging whole provider request/response or unfiltered JSON export.  
**Repair:** strict allowlist, redaction, purge contaminated analytics stores without destroying quota source, security review.  
**Retest:** grep for synthetic secret marker across storage/export/logs; fail release if any leak persists.

### T22 — Unknown model silently priced using another tier

**Cause:** substring or fallback price mapping.  
**Repair:** exact model ID + documented official alias only; mark unknown.  
**Retest:** two similar named models with different prices, unknown third model.

### T23 — Monthly cost estimate exceeds expected amount

**Cause:** sum of overlapping global/task/provider usage rows, or per-event rounding.  
**Repair:** aggregate unique operation facts once and high precision.  
**Retest:** 1,000 tiny events + disjoint filter sum property.

### T24 — Browser background suspension loses Applied counts

**Cause:** event stored only in worker RAM or event listener registered too late.  
**Repair:** privileged durable event writer and no reliance on in-memory lifetime.  
**Retest:** force worker stop immediately after Apply in controlled test.

### T25 — Custom range excludes last date

**Cause:** treating end date local midnight as exclusive without adding next calendar day.  
**Repair:** UI inclusive dates → internal next-local-midnight exclusive.  
**Retest:** one-day custom range including end-date 23:59.

### T26 — Last day appears twice after timezone switch

**Cause:** recalc buckets in current timezone while also retaining buckets in previous zone.  
**Repair:** one query source/timezone policy with coverage markers; dedup by operation ID where possible.  
**Retest:** switch Paris/UTC, sum once for overlapping instants.

### T27 — 'Delete' erases API provider billing records

**Cause:** misleading UI copy.  
**Repair:** clarify deletes **only local Correctly analytics**, not external provider history.  
**Retest:** UX copy and help docs reviewed; simulate deletion without network calls.

### T28 — First-run migration initializes false empty counts

**Cause:** treating failed read/corrupt existing V5.8 database as brand-new install.  
**Repair:** distinguish genuine fresh install from corrupted existing state, fail closed.  
**Retest:** missing DB fixture vs invalid existing policy fixture.

### T29 — Statistics fields disappear in French locale

**Cause:** dynamic translated keys used as persistence IDs, or missing translations.  
**Repair:** internal stable enums and explicit i18n messages.  
**Retest:** switch FR↔EN without changing stored query result.

### T30 — Dashboard cannot be used offline

**Cause:** remote chart script, dynamic currency API or provider fetch dependency.  
**Repair:** bundle assets locally and use local pricing registry.  
**Retest:** offline load/filter/export after seeded data.
