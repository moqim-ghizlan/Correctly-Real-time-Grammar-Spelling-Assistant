## 0. Mission, precise outcome, and strict boundaries

### 0.1 One-sentence mission

Make the existing V5.2 AI correction usable everywhere it is safely supported, through **three explicit user-initiated triggers**—keyboard shortcut, selected-text right-click menu, and a quiet contextual action button—feeding **one shared, accessible correction preview**; never silently edit or accidentally transmit content.

### 0.2 What V5.3 is (and is not)

- **Build:** production invocation UX and reliable selection capture; coordinated UI; unified request lifecycle; cancellation, copy, safe apply and undo; supported-editor coverage; settings to control triggers; browser tests.
- **Reuse:** V5.2's Gemini request/response parsing, correction rules, request accounting, stale-state checks, editor transaction and undo mechanisms. Refactor those only to expose clean APIs or fix proven bugs.
- **Do not build:** new provider implementation; new API keys; rewriting styles; translation; dialect UI; user-defined text expansion improvements; detailed statistics dashboards; full daily/weekly/monthly caps; Windows software, local servers, Java, Python runtime or LanguageTool.
- **No continuous AI:** no network requests from typing, input, selectionchange, focus, mousemove, scroll, observer callbacks, page load or button *appearance*. A request is caused only by deliberate activation of a correction command.
- **No automatic replacement:** Gemini never directly edits the page. The user must review and select Apply. Copy remains usable where safe Apply is unsupported.
- **Personal-only:** key belongs to the user, entered in extension settings. No shared hardcoded or bundled credential.

### 0.4 Product decisions and defaults

1. **Primary:** contextual, non-invasive **Correctly** action near the focused editable region, only when eligible; no permanent badge on all page text boxes.
2. **Fast path:** keyboard command defaults to **Ctrl+Shift+C on Windows/Linux**, if browser/OS permits. This is a preference, not a guarantee: shortcut collisions vary. Expose the actual registered browser shortcut in settings and link to the Chrome/Brave extension shortcut manager where possible; allow user customization through the browser rather than claiming to override it from page scripts.
3. **Fallback:** native browser context menu **Correctly → Correct selected text**, visible when a non-empty selection is present. If a second submenu action is shown, it must be non-networking, e.g., **Open settings**; do not show an active Rewrite option before V5.4.
4. All three routes must reach the **same correction controller** and preview contract; no duplicate provider calls or inconsistent text preparation.
5. **Selection first:** correct exactly the explicit selection. **No selection:** the focused editable's *current sentence* can be suggested **only if** V5.2 already supplies safe, unambiguous sentence extraction and range verification; otherwise show “Select text to correct.” Do not guess sentences in complex editors or scrape whole fields.
6. Preview must show original and proposal, including a clear no-errors state, per-editor safety state, request cost/limit error messages when available, and Apply / Copy / Cancel actions.
7. Default UI language follows supported existing extension conventions. In V5.3 use minimal existing locales (FR/EN if present); do not add the V5.5 language feature.
8. The action surface and preview must never obstruct normal text editing or hijack keyboard shortcuts without explicit user preference.
9. Preserve existing custom expansion behavior if present in repo; do not process expansion triggers as AI actions and do not rewrite protected abbreviations.
10. Do not assume every editor supports programmatic editing. Unsupported editors must degrade safely to **Copy suggestion**.

### 0.5 Non-negotiable invariants

- **N1:** No provider request without a verified user gesture.
- **N2:** No provider request containing sensitive input (password, one-time code, payment data or identifiable sensitive field) or text from disabled domains.
- **N3:** No unknown tab DOM scanning or harvesting unrelated page text.
- **N4:** Exactly one active correction operation per invocation; deduplicate accidental rapid repeat activation.
- **N5:** Original text stays unchanged until user explicitly clicks Apply; Cancel is no-op.
- **N6:** Before Apply, verify exact editor, selection/range, original substring, focused context where relevant, document state and whether result is current.
- **N7:** If safety cannot be established, disable Apply; enable Copy if a valid suggestion exists.
- **N8:** No API keys, sent text or complete AI responses in logs, telemetry, exception dumps or browser sync.
- **N9:** Disable trigger actions cleanly if a user setting or site-level exclusion demands it.
- **N10:** Existing V5.2 API limits must be checked in the shared request path, not separately with inconsistent counters in each trigger.

## 2. User journeys and acceptance examples

### 2.1 Keyboard with selected text

1. User types `Je suis aller a Lyon hier.` into supported editor.
2. User selects precisely `Je suis aller a Lyon hier.`
3. User presses configured shortcut.
4. The extension freezes an immutable text/range snapshot, validates domain/field and checks baseline quota.
5. Show loading state (“Checking text…”). Exactly **one** Gemini correction request.
6. Show before `Je suis aller a Lyon hier.` and after `Je suis allé à Lyon hier.`.
7. User clicks Apply. Only the selected content is replaced if source still matches snapshot.
8. Show optional Undo action; user can restore original if no intervening conflicting change.

### 2.2 Context-menu selected text

1. User selects a sentence in a textarea or (where supported) a normal `contenteditable`.
2. Right click: native `Correctly` → `Correct selected text`.
3. Context-menu click supplies selected text, but the extension **must not trust selected text alone as a writable DOM range**.
4. Recover/verify source tab, frame, editable host, live selection snapshot and immutable range. If unverifiable, proceed in **preview/copy-only mode**; never edit arbitrary nearby content.
5. Same Gemini flow and preview as keyboard; no different correction prompt.

### 2.3 Smart button near editor

1. Focus an eligible editable field. A compact action icon appears near the editable **without stealing focus**.
2. No network request occurs on showing it.
3. User selects text, then activates the action icon with mouse or keyboard.
4. Selection must survive focus changes caused by button interaction (capture safely on pointerdown/mousedown while respecting selection semantics; don't globally suppress focus).
5. Use verified selection or safe sentence logic; same controller and preview.
6. Button hides or repositions on blur, editor removal, viewport scroll/resize and disabled site; no ghost buttons.

### 2.4 No selection

- If robust supported sentence extraction is implemented in V5.2, show a clearly labeled “Current sentence” preview of the exact computed range, with opt-out/cancel before request if extraction is ambiguous.
- Otherwise display “Select a sentence or text to correct.” and do **not** call Gemini.
- In particular, never default to whole page, whole email conversation, an entire rich document or invisible text.

### 2.5 Sentence already correct

- Show “No corrections needed.” Keep exact original text; no Apply needed; one API use can still be billable.

### 2.6 Sensitive/unsupported field

- Password, email-like credentials, OTP, payment fields, disabled/read-only content: no action button/no request; context-menu/shortcut invocation returns a safe notice.
- Search/email/url/tel input types: follow the stricter actual V5.2 support policy; do not expand implicitly.
- On arbitrary read-only page selection: optional preview-only support **only if explicitly approved**, otherwise show “Select text inside a supported editable field.” The default is **do not send** unsupported page text.

### 2.7 Multilingual input

- Treat FR/EN based on V5.2 behavior; never force translation or professional rewriting.
- Keep punctuation, diacritics, line breaks and mixed-language names faithfully.

## 3. System architecture and communication

### 3.1 Preferred MV3 architecture

```text
Chrome / Brave web page (untrusted)
  └── content script (isolated world)
        ├── focused-editor tracker
        ├── selection snapshot adapter
        ├── contextual action overlay
        ├── preview UI (safe text rendering)
        └── guarded Apply / Copy / Undo
                 ↕ typed chrome.runtime messages
      extension background service worker
        ├── registered keyboard command handler
        ├── context-menu handler
        ├── trigger dispatch and tab/frame targeting
        ├── shared V5.2 correction request coordinator
        ├── existing quota checks / accounting
        └── Gemini API adapter (API key never sent to content scripts)
      extension options UI
        ├── trigger preferences and status
        └── shortcut manager instructions
```

- Content scripts may **request an operation**, but should not hold the API key or call Gemini directly.
- The service worker performs privileged network requests and validates message sender/tab/frame/origin where applicable.
- A keyboard `commands` event or `contextMenus.onClicked` event can arrive with service worker wake-up; design handlers to work after worker recreation.
- Page DOM is untrusted: never put response text into `innerHTML`, `insertAdjacentHTML` or dangerous attributes.
- All messages must be strict discriminated unions with bounded string lengths and request IDs. Ignore unrecognized messages.
- Register listeners at top level per MV3 lifecycle; do not register context menu items indiscriminately on every worker start.

### 3.2 Example *conceptual* message types (adapt to repo)

```ts
type TriggerSource = 'keyboard' | 'contextMenu' | 'floatingButton';

type Invocation = {
  kind: 'correctly:request-correction';
  version: 1;
  operationId: string;
  source: TriggerSource;
  editorSnapshotId: string;
  text: string;
  supportedEditor: boolean;
};

type PreviewResult = {
  kind: 'correctly:correction-result';
  version: 1;
  operationId: string;
  hasErrors: boolean;
  originalText: string;
  correctedText: string;
};
```

**Never blindly trust** `supportedEditor`, `originalText`, IDs, ranges or frame references supplied by page content. Validate against actual content-script state and sender metadata. Design identifiers as correlation, not authorization.

### 3.3 Shared coordinator contract

All three triggers call a single equivalent of `invokeCorrection({ source, tabId, frameId, ... })` and one V5.2 correction coordinator. Dispatch must not create a second parallel prompt, second quota deduction, or divergent text normalization. Centralize cancellation, request timeouts, current-operation invalidation, and error mapping.

### 3.4 Frame routing

- `tabs.sendMessage` with correct `frameId` when a verified frame is available.
- Never assume the main frame owns the selected text; many apps embed editors in iframes.
- Handle cross-origin and inaccessible frames gracefully; no blanket `all_frames` escalation without necessity.
- Context menu `frameId` metadata, when available, should guide routing; validate source against the live editable frame.
- If frame cannot be identified safely, show an error/copy-only flow rather than editing the wrong editor.

### 3.5 Minimal permissions

Inspect actual manifest first. Usually relevant: `contextMenus`, `commands` manifest declaration, `storage`, preexisting host permission for Gemini; potentially `activeTab` or `scripting` only if a justified preexisting injection strategy requires it. Do not add `tabs`, broad all-URLs hosts, clipboard permissions or native messaging by reflex. Document each added permission and why it is strictly required.

## 4. Keyboard shortcut — implementation in excruciating detail

### 4.1 Registration

1. Define a named MV3 command (e.g., `correctly-correct-selection`) in the final generated manifest.
2. Recommend `Ctrl+Shift+C` **only if accepted** by target browsers and not reserved. Note Chrome/Brave conflicts with DevTools, apps or OS shortcuts can prevent triggering.
3. Support browser shortcut management through `chrome://extensions/shortcuts` / Brave equivalent, using a normal clickable link or explanatory instructions where browser security allows.
4. Surface **registered command name / actual assigned shortcut** using `chrome.commands.getAll` where supported; do not assume suggestion equals active assignment.
5. Add an options row to enable/disable acting on the shortcut; disabling must be honored even if browser retains a registered command.

### 4.2 Event handling

- Attach `chrome.commands.onCommand` listener at background service-worker top level.
- Ignore commands other than exact known name.
- Retrieve active tab safely from available event `tab` context or `tabs.query` as permitted. Handle no tab, browser internal page, extension settings page, closed tab.
- Dispatch a narrow `capture-for-correction` message to correct eligible content script.
- Wait for validated immutable snapshot and only then request AI. Do not pull page text from `executeScript` unsafely.
- If frame not known, use a controlled focus ownership handshake; reject multiple ambiguous responses.
- Prevent two nearly simultaneous shortcut events from causing duplicate paid requests.

### 4.3 Focus and selection

- Snapshot native input/textarea selectionStart/End before asynchronous operations.
- For contenteditable, clone/record `Selection` range only with strict containment checks in a single supported editor.
- Capture the exact substring; Unicode surrogate pairs and combining marks must not yield split characters.
- Empty selection triggers documented no-selection behavior; do not send random text.
- If source editor is subsequently changed, moved, detached, or hidden, invalidate Apply.

### 4.4 Keyboard accessibility

- Escape closes preview without editing.
- Tab navigation reaches buttons in logical order.
- Enter/Space activate focused action, not arbitrary Apply by default.
- Do not steal or prevent browser's normal undo, copy, paste or Enter typing.
- Use focus restoration to original editor only if still mounted and safe; avoid replacing selection unexpectedly.

## 5. Context menu — implementation in excruciating detail

### 5.1 Menu design

- Parent: **Correctly**.
- Child: **Correct selected text**.
- Optionally: **Open Correctly settings** only if useful.
- Prefer `contexts: ['selection', 'editable']` only after checking browser semantics and ensuring selection is truly eligible; menu visibility alone does **not** authorize sending text.
- No placeholder enabled menu for future rewrite feature.

### 5.2 Safe registration

- Register IDs deterministically when extension installed/updated, e.g., `runtime.onInstalled`; handle idempotence and `contextMenus.removeAll` with care (it only removes your extension's menus but can create timing issues).
- Do not register the same menu in a way that races on every service worker resume.
- Reinstall/update must leave exactly one parent and one correction item.
- Add test for install/update/restart and error `duplicate id`.

### 5.3 Click routing

- `contextMenus.onClicked(info, tab)` verifies menu ID, tab ID, URL/domain exclusion, source frame and selection availability.
- `info.selectionText` is useful as a cross-check but **not enough to apply**: plain selection text does not locate editable range.
- Context-click can remove a visual selection or focus; preserve a *short-lived* last-selection snapshot in content script only if obtained through trusted user selection before the menu, bound to editor/range/current document.
- Compare selected text to snapshot, require exact match and fresh TTL; if not verifiable, do not Apply.
- If only selectionText exists but editor not traceable, return notice (default) or a clearly copy-only preview if product permits; no synthetic arbitrary insertion.
- Right click on one tab must never cause correction in another tab.

### 5.4 Cross-page exclusions

- Cannot inject on `chrome://`, `brave://`, Chrome Web Store, protected PDFs/embedded viewers, extension pages and inaccessible cross-origin contexts. Tell user simply: “Correctly cannot edit this page.”
- Avoid promising universal access to all sites.

## 6. Contextual smart button — design and lifecycle

### 6.1 Desired UX

Small recognizable correction action (icon + accessible label/tooltip) close to the currently focused eligible editable. Show only when needed. No flashing, shifting layout, full-screen floating obstruction, overlay duplication or unexpected content replacement.

### 6.2 When to show/hide

**Show:** supported editable is focused, not sensitive, domain not disabled, trigger enabled, UI not blocked; optional minimum content/selection checks.  
**Hide:** blur outside editor/overlay after guarded handoff, editor detached, navigation/unload, disabled option, page enters fullscreen if obstructive, element becomes readOnly/disabled, modal/preview closes as required, unsupported field recognized.  
**Reposition:** viewport scroll, zoom changes, window resize, editor bounding box changes; throttle via animation frame and avoid per-keypress full DOM traversal.

### 6.3 Injection architecture

- One container/root per document, reused and cleaned on shutdown; Shadow DOM may isolate styles if supported but not a security boundary.
- Use `textContent` for all user/model text; CSS scoped so site styles do not leak; keep z-index reasonable.
- Prevent click from losing text selection: capture a valid snapshot before focus handoff, or explicitly retain selection on pointer activation without interfering with accessibility.
- Pointer and keyboard activation must both work; test touch where available.
- Align relative to visible editor edge and viewport boundaries; flip to opposite side near borders; avoid covering caret and native autocomplete.
- For iframe, render in the frame hosting editable when possible, not necessarily top page; never draw on inaccessible frame's behalf.
- Avoid expensive polling and broad MutationObserver scans. Observe relevant active editor changes as needed.

### 6.4 User preference

Settings toggle **Show smart action button**, default ON. Changes propagate to open tabs reliably using storage events/messages; disabling removes UI without page reload where feasible and no stray listeners remain.

### 6.5 Prevent CSS and UX regressions

Test pages with `transform`, `position: fixed`, `overflow: hidden`, high z-index overlays, right-to-left layout, mobile-size viewport, fullscreen, browser zoom 80/125/200%, and dark mode. Verify the button remains usable and does not intercept user page controls.

## 7. Unified correction preview — exact requirements

### 7.1 States

`idle → capture → validating → quotaCheck → requesting → completedNoErrors | completedWithSuggestion | failed | aborted | stale`.  
From `completedWithSuggestion`: `applyAttempt → applied | stale | unsupported`, with Copy and Cancel always available when meaningful.  
Only one authoritative operation ID at a time per active editor. A late response from an older invocation must never replace a newer preview.

### 7.2 UI content

- Title: “Correctly — Correction”.
- Source label: “Original” with exact immutable snapshot text.
- Suggestion label: “Suggested correction” with trusted validated AI output rendered as plain text.
- Loading message and loading indicator without repeated duplicate requests.
- A clear no-error state with Close.
- Error states: missing key, quota reached, invalid key, network unavailable, upstream rate limit, timeout, invalid response, unsupported editor, text changed, protected field. Use user-friendly wording and optional Settings link.
- Buttons: **Apply**, **Copy**, **Cancel / Close**; **Undo** when supported following Apply.
- Destructive/unavailable Apply reason surfaced without hiding Copy.
- Accessible dialog semantics `role="dialog"`, `aria-label` / `aria-labelledby`; appropriate `aria-live` progress; focus trap only for true modal, and restore prior focus responsibly.

### 7.3 Layout and interaction

- Popup fits narrow windows; long text constrained with internal scrolling and wrapping, preserve newlines.
- Support dark/light existing theme and high-contrast; target WCAG-style keyboard and readable focus indicators.
- Avoid rendering HTML provided by the page or model. Never run returned markup as code.
- Do not make Apply look enabled when editor adapter cannot guarantee the exact edit.
- No surprise auto-close before user can read result; avoid permanent intrusive panels.
- If navigation occurs while waiting, abort/ignore stale result and do not inject into a new page.

### 7.4 Copy handling

- Copy correction should use best permitted browser clipboard mechanism only after direct user gesture; handle denial with an informative message.
- Do not request privileged clipboard permissions if clipboard can work with existing user gesture.
- Copy never changes the source editor and must not be logged.

### 7.5 Undo handling

- Reuse V5.2 guarded transaction journal. Restore only if the exact applied text is still present in the expected editor and no conflicting intervening edit occurred.
- Honor native `Ctrl+Z` behavior where it functions; do not intercept globally or falsely guarantee it across all editors.
- If safe undo is unavailable, disable or hide custom Undo and say why.

## 8. Selection integrity and editor-specific policy

### 8.1 Supported baseline

- `textarea` with valid selection offsets and appropriate event semantics.
- `input[type=text]` only if V5.2 explicitly supports it; not password, email, URL, tel, search, number or hidden input unless previously approved with evidence.
- Simple single-node `contenteditable` if V5.2 transaction adapter supports reliable capture/apply.
- Rich editors (ProseMirror, Slate, Quill, Gmail compose, Google Docs, Monaco, CodeMirror, iframe editors): **evaluate individually; default to Copy-only or unsupported**, never mutate arbitrary DOM and assume editor state remains valid.

### 8.2 Snapshot schema (conceptual)

Store operation ID; origin tab/frame; page URL/origin as needed for exclusion; editor identity based on live weak reference in content script (not serializing DOM node); exact selected text; selection offsets/range or conservative editor hash; capture timestamp; language metadata if V5.2 uses it; text length. No API key and no persistent full text.

### 8.3 Apply preconditions

1. Same connected editor instance / frame / document.
2. Not disabled, readOnly or sensitive.
3. Same original substring at recorded range.
4. No overlapping composition IME (`compositionstart` → `compositionend`).
5. Selection/range remains representable after reflow; no stale offsets.
6. Candidate is a valid V5.2 response and still tied to current operation ID.
7. Apply with appropriate input/editor events only for supported adapter.
8. On failure, original content stays untouched; user can Copy.

### 8.4 Intervening edits

If user changes *anything* relevant while Gemini responds, either invalidate Apply outright (safest default) or prove an exact isolated non-conflicting replacement. Do not casually rebase offsets; never silently apply to a changed sentence.

### 8.5 Controlled front-end frameworks

Native DOM changes can be overwritten by React/Vue state or can break undo. Use previously tested V5.2 adapter only. If no safe adapter, copy-only. Browser tests must detect rollback on next keypress and disable Apply for that editor.

## 10. Privacy, security and cost constraints

1. No network request from focus, selection or contextual-button appearance.
2. Correctly UI may use only extension-safe resources; no remote script injection or eval.
3. No page-level global API key access, DOM attributes containing keys or unsafe message broadcasting of credentials.
4. Existing V5.1 user-configured quota check must run before calling Gemini; count attempts according to its documented semantics.
5. For retries: never automatically retry paid generation as a separate request unless existing V5.2 policy explicitly and safely permits it; avoid duplicate billing.
6. On user double click, coalesce requests; no duplicate call from menu + shortcut within a single pending capture.
7. Limit selected text length and preview memory according to V5.2. A large selection should be rejected gracefully before network activity.
8. No automatic requests when domain is disabled or context is private/sensitive.
9. Local API quotas are not absolute billing caps. Do not tell user they can guarantee provider spending from extension controls alone.
10. Browser storage containing raw API keys is accessible to a sufficiently privileged local attacker or compromised extension; do not claim it is encryption-grade protection.

## 15. Troubleshooting playbook — symptom → cause → remedy → regression test

### T01: Keyboard shortcut does nothing

Possible causes: manifest command missing, incorrect generated manifest, reserved combination, shortcut not assigned, background listener not active, browser permissions.  
Remedy: inspect installed manifest and `chrome.commands.getAll`; visit extension shortcut manager; check onCommand listener registration at worker top-level; change suggested shortcut if conflict.  
Regression: K01/K05/K08.

### T02: Shortcut works on simple page but not embedded editor

Possible causes: wrong frame, inaccessible cross-origin iframe, focus tracking in main frame.  
Remedy: use event/source frame and validated content-script handshake; opt out where inaccessible. Never fall back to arbitrary top-page text.  
Regression: K12/M05.

### T03: Right-click menu duplicates after restart

Possible causes: registration each service-worker wake or duplicate menu IDs.  
Remedy: register in a controlled lifecycle and use stable IDs; inspect browser API errors.  
Regression: M07/M08.

### T04: Context menu clicked but selected text is lost

Possible causes: context menu steals focus, live Selection clears, snapshot not retained.  
Remedy: capture a bounded, editor-bound selection snapshot on trusted selection event; verify equality and TTL when the menu command arrives. If not verifiable, refuse Apply.  
Regression: M03/M04.

### T05: Smart button disappears when clicked

Possible causes: blur handler destroys overlay before pointer activation.  
Remedy: define explicit focus handoff between editor and action; snapshot on pointerdown; delay destruction until action is resolved, without global event suppression.  
Regression: B04/B06.

### T06: Smart button covers other UI or leaves duplicates

Possible causes: incorrect positioning, duplicate mounting, missing cleanup on SPA navigation, zoom assumptions.  
Remedy: singleton root per frame; track active editor; use bounding rect/viewport clamping; cleanup event listeners and observers.  
Regression: B02/B07/B10/S10.

### T07: Clicking Apply corrupts text or inserts at wrong cursor

Possible causes: stale selection offsets, editor re-render, focus movement, wrong frame, Unicode handling, unsupported framework DOM mutation.  
Remedy: **block Apply immediately**; reproduce with test fixture; enforce V5.2 transaction preconditions and downgrade unsupported editors to Copy-only. Never “solve” with arbitrary `document.execCommand` fallback.  
Regression: P04/P07/P12.

### T08: API is called two or three times for one action

Possible causes: content script and worker both trigger, duplicated event listeners, double click, retry loop.  
Remedy: one authority for request coordinator; operation ID dedup; stateful in-flight lock and stable listener lifecycle.  
Regression: K06/P13/S01-S03.

### T09: Gemini key visible in page or logs

Possible causes: key passed into content script, dumped storage in console, endpoint key in UI, error serialization.  
Remedy: stop release; remove logs; keep key only in extension-private storage and worker fetch; sanitize error mapping; add secret-scanning tests. Rotate compromised key.  
Regression: S06 + network/source inspection.

### T10: Corrections on password or disallowed pages

Possible causes: coarse `contenteditable` check, missing domain exclusion on one trigger, trusting menu selection text.  
Remedy: move sensitive-field and domain checks into shared request coordinator *and* content adapter; deny by default.  
Regression: S04/S05.

### T11: Preview shows old result for new selection

Possible causes: late async response, operation ID not checked, worker restarts.  
Remedy: track latest accepted invocation, discard/close prior results; do not apply from outdated snapshots.  
Regression: P09/P20.

### T12: Context menu or shortcut unavailable after browser update

Possible causes: changed browser extension permissions, shortcut assignment, incorrect manifest bundling.  
Remedy: reinstall unpacked build and inspect actual runtime; document genuine browser limitations; keep other trigger paths as fallback.  
Regression: browser reboot acceptance.

### T13: The page becomes slow during typing

Possible causes: global MutationObserver full-tree scanning, remeasuring overlay on each keypress, excessive document listeners, CSS layout thrash.  
Remedy: track focused editor only; throttle reposition; cleanup on detach; profile before/after typing; never involve API during typing.  
Regression: B03/S10.

### T14: Clipboard copy silently fails

Possible causes: clipboard permissions or lost user gesture in async handler.  
Remedy: perform copy on direct click, catch permission failures and show explicit error; provide manual select-and-copy fallback.  
Regression: P05.

### T15: Native Ctrl+Z behaves inconsistently

Possible causes: programmatic input methods and framework-specific history.  
Remedy: preserve V5.2 guarded custom Undo where supported; accurately document native undo limitations; never globally override Ctrl+Z.  
Regression: P06.
