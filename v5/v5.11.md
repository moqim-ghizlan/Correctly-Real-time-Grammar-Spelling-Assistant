## 1. Exact approved product contract

### 1.1 Handle

A small **semicircle**, with the Correctly logo, is attached to the **right edge of the page viewport**. It is not a fully circular button and is not anchored to a text field. At rest it is subtle. On hover it grows **slightly** and smoothly. Clicking it opens the modal. Dragging with the pointer held moves it up or down along the right edge, not left or right. Its default vertical coordinate is viewport center; after dragging, its chosen vertical position should be restored (see persistence proposal).

The handle **disappears whenever the modal is visible** and reappears when it is hidden, regardless of which entry point opened the modal. A drag must not accidentally open the modal.

### 1.2 Modal

One **in-page modal centered in the browser viewport**, with the same fixed outer dimensions across all three tabs. Its content area scrolls vertically when necessary, with a scrollbar on the right; the header, tab navigation and two header actions remain visible while content scrolls. It is **not resizable** by the user. On a viewport smaller than the preferred dimensions, clamp to available space without overflow: responsive safety is not user resizing.

The upper-right header has exactly **two controls**: **Settings** (gear, opens the extension's existing Settings/options page) and **Hide** (minimize/eye-off/chevron icon, hides the modal). **Do not add an X button.** No third header action.

### 1.3 Three tabs

**Correction**, **Reformulation**, **Translation**. Switching tabs never closes the modal. Each tab has its own operation options and a **deliberate Generate** control. The same input text is shared and editable across all tabs. Every fresh opening starts at **Correction**.

### 1.4 Opening and reset

Open by **(a)** semicircle click, **(b)** Ctrl+M, **(c)** extension icon in Chrome/Brave toolbar. All three invoke one modal controller and render the same in-page UI, **not** a browser-action popup. At opening, use the current valid selected text if available; otherwise show an empty input. Opening alone makes no AI request. Each hide/dispose and next open starts a fresh session: clear text, results, temporary tab options and active tab. Persist long-lived extension settings (provider, language preferences where they are existing global settings, keys, quotas, statistics) unchanged.

### 1.5 Result and Apply behavior

Generated results stay in their respective tabs while modal remains open and input is unchanged. A change to shared input clears all generated results, preventing stale output. **Apply** replaces only the verified original selected text in a writable page editor and hides modal after successful commit. **Copy** copies the generated result without hiding. Without a verified editable target, **Apply is disabled** and Copy remains possible. After a successful Apply, offer **Undo for five seconds**; Undo must use the existing safe transaction mechanism.

## 2. Semicircle handle: visual geometry and placement

### 2.1 Shape and anchoring

- Render a visible **half-disk/semicircle** emerging inward from the right viewport edge; its flat side aligns with the right edge and its curved side faces the page. Do not render a full circle or horizontal pill.
- Correctly logo centered optically inside the visible shape; use the existing approved local asset if available, or a bundled static SVG. No remote icons.
- `position: fixed` in the page viewport (or equivalent compatible overlay positioning). It is **not** positioned relative to a textarea, selection rect, or cursor.
- Default vertical center at 50% of the current visible viewport. Clamp to a top/bottom safe margin so it never becomes unreachable.
- Its horizontal position stays locked to the right edge even when dragged.
- Use high enough stacking to be usable, without covering browser chrome or untrusted page dialogs unnecessarily.

### 2.2 Proposed visual tokens — not owner-approved exact numbers

| Token | Suggested value | Reason |
|---|---:|---|
| Handle visible height | 48 px | Usable target |
| Handle visible inward width | 25 px | Semicircular silhouette |
| Handle hover scale | 1.08 | Small increase only |
| Hover transition | 140 ms ease-out | Subtle |
| Right inset | 0 px | Attached to edge |
| Top/bottom drag margin | 16 px | Prevent unreachable handle |
| Handle icon | 17–20 px | Legibility |
| Modal preferred width | 640 px | Proposed starting point |
| Modal preferred height | 520 px | Proposed starting point |
| Modal max viewport width | calc(100vw - 24px) | Safety on small windows |
| Modal max viewport height | calc(100dvh - 24px) | Safety on small windows |

**The owner approved fixed dimensions, not these particular pixel values.** The agent should calibrate the exact preferred size against the approved screenshots and current UI, and document the selected numbers. Modal size must remain identical across tabs.

### 2.3 Theme

Use the previously chosen refined dark/glass visual direction as inspiration for the **semicircle and modal**, not for a three-action pill. Maintain high contrast and coherent light/system theme behavior if already supported. Avoid over-glowing, continuous animation or colorful mismatched icons. Include a solid-color fallback if backdrop blur is unsupported or unreadable.

### 2.4 Placement persistence

Recommended: save a normalized vertical fraction `yRatio` in existing extension settings storage, scoped to the user's browser profile, default `0.5`. Clamp on viewport resize and restore on subsequent pages/reloads. Do **not** persist screen pixels that break on resize. The user approved moving the handle but did not explicitly specify whether the position is global or per-site: use a single global preference as a conservative implementation default, and document it as an assumption rather than a confirmed product decision.

## 3. Semicircle pointer and drag behavior

### 3.1 Pointer flow

- On primary `pointerdown`, capture start coordinates and potential gesture; do not open modal yet.
- If vertical displacement exceeds a small drag threshold (proposed 6 CSS px), enter dragging state.
- While dragging, update only Y; keep X fixed at right edge; clamp within viewport safe bounds.
- On `pointerup`, if dragging occurred, save position and **do not** open modal. If no drag occurred, treat as click and open modal exactly once.
- Handle `pointercancel`, lost capture, window blur and destroyed nodes safely. Do not leave dragging stuck.
- Avoid duplicate activation from pointerup followed by click. Prefer one consistent event contract.
- Pointer and touch behavior should be usable; do not block page scroll globally. `touch-action: none` only on the small handle if needed.
- Keyboard activation via Enter/Space opens modal; provide a non-pointer method to reposition only if accessibility review finds it necessary (proposed arrow keys when handle focused), without conflicting with existing shortcuts.

### 3.2 Drag versus click acceptance

| Gesture | Result |
|---|---|
| Hover | Slight enlargement, zero API calls |
| Mouse click/release with no drag | Open modal once |
| Hold and move vertically | Move handle, do not open modal |
| Move horizontally while dragging | Horizontal coordinate unchanged |
| Drag above viewport | Clamp to top safe margin |
| Drag below viewport | Clamp to bottom safe margin |
| Open modal during handle hover | Handle becomes hidden |
| Hide modal | Handle returns at last chosen Y |
| Reload page | Restore persisted Y (if persistence implemented) |

## 4. Three entry points and browser-action behavior

### 4.1 Unified controller

All triggers must call one semantic action: `openUnifiedModal(source, verifiedSelectionContext?)`. They must not implement three separate modals or diverging initial tabs. Modal opening is idempotent: if already open, focus the existing modal instead of resetting it or creating another. **Reset applies to a new opening after hiding**, not repeated open signals while it is already visible.

### 4.2 Ctrl+M

Register **Ctrl+M** as requested. Prefer a supported `chrome.commands` registration if possible, but inspect existing V5 shortcut mappings and browser conflicts first. Browser/website/system shortcut collisions may prevent delivery; do not claim the extension can override every browser shortcut. Avoid global `preventDefault()` when the extension does not actually own the event. On macOS, platform-specific shortcut mapping requires testing; do not silently promise Ctrl+M everywhere.

### 4.3 Extension toolbar icon

The **browser toolbar extension icon** must open the **in-page centered modal in the active tab**, not a default action popup. Inspect `manifest.action.default_popup` and the existing action click handler. If a default popup exists, it usually intercepts `chrome.action.onClicked`; remove/adjust only after migrating any essential popup features to their appropriate existing pages or controls. Never silently delete functionality.

On action click, identify the active tab, check permissions/restricted URL/frame support, and send a typed `OPEN_MODAL` command to its existing content script or use the project's approved injection strategy. Validate tab identity and sender. **Do not create a new tab containing the modal**. If the active page is restricted (e.g. browser-internal URLs, extension stores, certain PDFs), report the limitation safely; do not claim guaranteed injection.

### 4.4 Selection availability across triggers

Selection must be captured **before clicking the launcher or browser chrome causes the page selection to collapse**. Reuse the existing selection snapshot logic and validated editor identity. For toolbar-icon invocation, the background service worker cannot directly read the page selection: ask the active content script for its last valid snapshot, subject to freshness/identity checks. If unavailable, open with empty text rather than inventing a selection.

### 4.5 Trigger matrix

| Entry point | Visible modal | Initial tab | Prefill | Handle state | API calls on open |
|---|---|---|---|---|---|
| Semicircle click | Same centered modal | Correction | Valid selection or empty | Hidden | 0 |
| Ctrl+M | Same centered modal | Correction | Valid selection or empty | Hidden | 0 |
| Browser extension icon | Same centered modal | Correction | Valid selection or empty | Hidden | 0 |

## 5. Modal shell, dimensions, scroll and header

### 5.1 Geometry

- One centered overlay per supported active document/frame; consistent dimensions across tabs.
- The **outer frame must never grow or shrink because the user changes tabs or receives a longer result**.
- Fixed header, fixed tabs and stable footer action area where appropriate; **only the central content panel scrolls**.
- Show a right-side scrollbar within the content region when content overflows. Do not make the whole webpage scroll to reach the modal's own content.
- At viewport widths/heights below preferred modal size, clamp outer dimensions to fit safely, preserving accessible controls and internal scrolling. This is responsive fallback, **not** a user-resizable modal.
- Support zoom, browser window resize, RTL content, long words, multiline outputs and long translations.

### 5.2 Header

Left: Correctly identity/title. Right: **exactly two icon buttons** in this order unless design review justifies another order: **Settings gear**, **Hide/minimize**. **No X close button.** Both must have accessible names/tooltips.

**Settings:** open the extension's existing options/settings page through a trusted extension API (`chrome.runtime.openOptionsPage()` or established route). Do not replace it with an invented new settings modal. Opening Settings should not start AI work. If modal remains visible in original tab, keep session safe; user did not specify that Settings auto-hides the modal.

**Hide:** immediately hide modal, dispose transient session state and show semicircle again. No text is applied, copied or submitted automatically. Cancel pending operations safely using existing cancellation support or ignore late results using session IDs; never allow a stale response to resurrect the hidden modal.

### 5.3 Tabs and content

Three persistent tab controls: Correction, Reformulation, Translation. Active tab is visually distinct and screen-reader identifiable. Switching tabs changes only the content panel, preserving shared input and per-tab results while the session remains open. Tabs/header remain visible when content scrolls. Default active tab at every fresh opening: **Correction**.

### 5.4 No third header button

Do not implement an X, maximize, pop-out, pin, or a third header action in V5.11. The owner specifically replaced the conventional X with **Hide** and **Settings**.

## 6. Session reset, shared input and result lifecycle

### 6.1 Fresh opening contract

On every transition from **hidden → open**, initialize a new `sessionId`, set active tab `correction`, set shared input to valid currently selected text (or `''`), clear all three results/errors/loading states, and reset temporary tab choices to established defaults. Do **not** wipe permanent extension settings, credentials, quotas or usage history. If the same modal is already open, additional open events should only focus it, not destroy active work.

### 6.2 Shared input

One canonical `sharedText` in the modal controller. Every tab renders/edits this same value; no separate correction/rewrite/translation text copies. Updating it in any tab updates the others. Preserve multiline Unicode, emoji, French accents, Arabic/RTL and whitespace. Do not use unsafe HTML injection for text.

### 6.3 Result caching and invalidation

Each tab owns its generated result and its generation metadata, **associated with a particular input revision**. Switching tabs retains the result while `sharedText` is unchanged; no additional API request. Any actual change to `sharedText` increments `inputRevision`, clears results/errors for **all three tabs**, and invalidates or aborts in-flight generation for previous revision. Merely focusing a field, selecting text within it, or switching tabs is **not** a text change.

### 6.4 Late response safety

Every generation captures `(sessionId, inputRevision, operationId)`. On resolution, display output only if session still open, IDs match and input revision is unchanged. Old results must never overwrite newer text, trigger Apply, or reopen hidden UI. Cancelling UI display does not guarantee a remote billable request was cancelled; preserve honest quota accounting.

### 6.5 Examples

| Scenario | Expected |
|---|---|
| Open with selected text | Shared field prefilled, Correction active, no result |
| Open without selection | Shared field empty and editable |
| Correct, switch to Translation, return | Correction result still visible, no new request |
| Generate Translation, return to Correction | Each tab's prior result remains |
| Edit input in Translation | Correction/Reformulation/Translation results all cleared |
| Hide, reopen with no selection | Empty input, Correction tab, no old results |
| Hide, reopen with new selection | New selection prefilled, Correction tab |
| Open signal while already open | No reset and no duplicate modal |

## 7. Correction tab

- Shared input editor, prefilled or blank.
- **Generate correction** button; no generation on tab activation or text prefill.
- Existing grammar/spelling correction behavior and provider route retained; preserve existing result validation and any unchanged-text/no-errors state.
- Show result in readable preview separate from input, with safe text rendering.
- Present **Apply** (when original selection target verified), **Copy**, and **Cancel** per existing operation semantics; use modal-level Hide in header.
- Cancel an uncommitted result or pending operation without editing webpage; precise presentation may reuse existing V5 preview pattern.
- Preserve existing quota errors and provider errors; never silently retry.

## 8. Reformulation tab

- Same shared input, no duplicate independent input state.
- Preserve existing V5.4 rewrite style/tone choices, multi-style selection, batch semantics, candidate comparison and validation **to the extent actually present in code**.
- Options are contained **inside this tab's scrollable content**, not in an anchored mini-popup or three-button toolbar.
- Explicit **Generate reformulation** action after selecting options.
- Show candidates and existing selection behavior; each candidate can be copied and the chosen candidate applied safely.
- No model request when opening tab, hovering a style or changing options.
- Cache generated candidates for unchanged input until hide or input edit; option changes after generation must not misrepresent a result as matching newly selected options. Mark prior result stale or clear that tab's result if its generation options change; do not invalidate other tabs unless shared input changes.

## 9. Translation tab

- Same shared input.
- Preserve existing source/target language selection, automatic detection, supported dialects (including Syrian Arabic where implemented), direction handling, and any combined translation/rewrite workflow from V5.5.
- Options live **inside this tab's scrollable panel**.
- Explicit **Generate translation** action; changing language/dialect does not call provider.
- Display RTL text with correct direction and readable wrapping; use `dir=auto` for user/model text where appropriate.
- Apply selected output only through existing safe editor adapter; Copy available without editable target.
- If language/dialect choices change after generation, mark that tab's result stale or clear it; do not claim an old result was generated with the new options.

## 10. Results, Apply, Copy, Cancel and Undo

### 10.1 Apply

- Enabled **only** if a verified, writable original page editor and exact selected range/context are still valid.
- On click, invoke existing guarded Apply transaction. Do not search the page for matching text or paste into the currently focused arbitrary field.
- **Only after successful Apply**, hide modal automatically and reveal the right-edge semicircle.
- On failed/stale Apply, keep modal open, explain safe failure, and allow Copy.
- Never perform Apply merely because generation succeeded.

### 10.2 Copy

- Copies chosen generated result to clipboard using the existing safe path.
- Does **not** hide modal or mutate webpage.
- Copy remains available even if Apply is disabled (when result exists and clipboard access is available).
- Do not copy automatically on generation or on Hide.

### 10.3 Cancel

- Retain existing Cancel semantics for discarding pending or preview actions, without webpage mutation.
- The modal's header **Hide** is the session-level dismissal control; Cancel must not secretly replace it with an X or close behavior contrary to the agreed UX.
- When request cancellation is not guaranteed, invalidate session/revision result acceptance and avoid dishonest cost claims.

### 10.4 Undo toast / affordance

- After successful Apply, show an accessible, unobtrusive **Undo** affordance on the page for **5 seconds**. Modal is hidden, handle is visible.
- Undo must call the existing guarded reverse transaction and only restore when editor/range state still permits it. No blind overwrite of newer edits.
- Timeout dismisses the Undo affordance; it does **not** silently undo or edit anything.
- If user navigates or editor detaches, disable/remove Undo safely.
- Repeated Apply events must not produce duplicate undo transactions.

### 10.5 Buttons per tab

The approved prior modal pattern includes **Apply, Copy, Cancel**, with an explicit **Generate** button appropriate to each tab. Keep the header **Settings** and **Hide** globally. The owner did not approve new unrelated controls; avoid adding extra persistent buttons.

## 11. Selection capture, editable target and security

### 11.1 Capture

- Reuse V5.2/V5.3's existing editor identity, selected offsets/ranges, source text, frame ID and freshness checks.
- Capture a valid selection before handle or toolbar interaction can steal focus. Browser icon and Ctrl+M must use the same verified snapshot route.
- Selection outside writable editors can prefill shared input where permitted, but **Apply remains disabled**; Copy works.
- No selection means empty input; do not silently grab the entire webpage or whole focused field.

### 11.2 Editing manually does not authorize a new target

When a user edits shared input, the original target remains valid **only if** the existing transaction adapter can prove safe replacement of the originally selected text. Never infer writable destination from shared text equality. If original selection becomes stale, disable Apply. The owner requested safe direct replacement where possible, not unsafe force-write.

### 11.3 Protected fields

Never read from or inject into password, OTP, payment, sensitive or disabled/read-only fields in violation of existing exclusions. Do not bypass site allow/deny lists. No raw provider key or prompt goes into page DOM attributes, logs or analytics. Treat all selected text and model output as untrusted text.

## 12. Modal and handle state machines

```text
PAGE_READY
  ├─ modal hidden -> HANDLE_VISIBLE (default Y=50% or saved Y)
  │   ├─ hover -> HANDLE_HOVERED -> HANDLE_VISIBLE
  │   ├─ drag -> HANDLE_DRAGGING -> HANDLE_VISIBLE (new Y saved)
  │   └─ click -> OPEN_MODAL
  ├─ Ctrl+M -> OPEN_MODAL
  └─ extension toolbar icon -> OPEN_MODAL

OPEN_MODAL
  ├─ create fresh session (only if previously hidden)
  ├─ capture valid selected text or empty
  ├─ set tab=Correction
  ├─ hide handle
  └─ MODAL_OPEN

MODAL_OPEN
  ├─ switch tab -> MODAL_OPEN (same text, cached results)
  ├─ edit shared text -> invalidate all results -> MODAL_OPEN
  ├─ explicit Generate -> REQUEST_PENDING -> RESULT / ERROR
  ├─ Copy -> MODAL_OPEN
  ├─ Settings -> open existing options page; MODAL_OPEN unless user hides
  ├─ Hide -> discard transient session -> HANDLE_VISIBLE
  └─ successful safe Apply -> discard session -> HANDLE_VISIBLE + UNDO_5S

UNDO_5S
  ├─ safe Undo click -> guarded restore; dismiss
  └─ 5000ms expiry -> dismiss
```

**Never** let stale provider responses reopen a hidden modal. A handle drag is not a click. A click on extension icon while modal already open does not reset input or duplicate root.

## 13. Suggested component and message architecture

```text
Chrome/Brave toolbar icon
   └─ trusted background chrome.action.onClicked
        └─ typed OPEN_MODAL message to active eligible tab
Ctrl+M chrome.commands / approved keyboard listener
   └─ typed OPEN_MODAL
RightEdgeSemicircle (content script, fixed right edge)
   └─ OPEN_MODAL
                    ↓
UnifiedModalController (one per eligible active frame)
   ├─ sessionId / sharedText / inputRevision / activeTab
   ├─ existing editor selection snapshot adapter
   ├─ ModalShell (fixed-size, centered)
   │    ├─ Header: Settings | Hide
   │    ├─ Tabs: Correction | Reformulation | Translation
   │    ├─ SharedTextEditor
   │    ├─ ScrollableTabPanel
   │    └─ Generate / Result / Apply / Copy / Cancel
   ├─ per-tab result cache + request correlation
   ├─ safe Apply/Undo transaction adapter
   └─ existing trusted background operation dispatcher
        ├─ authorization + provider profiles
        ├─ quota admission and request journal
        ├─ Gemini/OpenAI routes
        └─ usage statistics
```

### 13.1 Isolation

Prefer one idempotent content-script UI host with scoped CSS/Shadow DOM where compatible. Shadow DOM prevents many CSS collisions but is not a security boundary. Use typed messages and existing permission checks. No new frontend framework by default. Do not embed provider keys in content scripts.

### 13.2 Multiple frames

One visible modal per invocation. If an editor lives in a supported iframe, the frame holding the valid selection may own the operation, but the visible modal must not duplicate in parent and child. Coordinate frame identity using existing messaging; if safe cross-frame mapping is unavailable, use copy-only/empty fallback and report limitation. Do not guess range coordinates across origins.

### 13.3 Lifecycle

Mount once per document/frame as permitted. Destroy listeners, timers, pointer capture, pending animations and observers on disable/navigation. Prevent duplicate Ctrl+M handlers or action messages after SPA navigation. Do not retain full selected text longer than the active session requires.

## 14. Styling, themes, animation and accessibility

### 14.1 Visual direction

Modern restrained dark-first glass aesthetic from the owner's approved visual references, applied to **semicircle + central modal**. Use cohesive neutral surfaces, soft border, gentle shadow, restrained accent, rounded corners, consistent icons. Light and system appearance must remain legible where supported. No neon, pulsating gradients, continuous shimmer or remote fonts.

### 14.2 Interaction details

- Hover grows semicircle slightly; no AI call.
- Modal appears with short unobtrusive fade/scale; no large sliding motion.
- Tabs show clear active state; keyboard focus visible.
- Header controls have clear iconography and tooltips.
- Generate shows loading only for actual pending operation.
- Content scroll stays inside modal; header/tabs remain visible.
- Respect `prefers-reduced-motion` and forced-colors modes.

### 14.3 Accessibility

Use real buttons with `aria-label`; modal `role=dialog`, `aria-modal=true` where focus/inert behavior is correctly implemented; named heading; tablist/tab/tabpanel semantics; proper active state; keyboard Tab/Shift+Tab and arrow navigation for tabs. Trap focus appropriately while modal is open without corrupting source selection snapshot. On Hide, restore meaningful focus where safe. Escape handling should not contradict the deliberate Hide-only header choice: if Escape dismisses, document it as keyboard equivalent of Hide, not a visible X. Do not override native browser shortcuts globally. Provide sufficient contrast and reachable hit targets.

### 14.4 Scroll and layout verification

Test long correction previews, multi-candidate reformulation, language dropdowns, Arabic paragraphs, 200% zoom, 320px narrow viewport, short-height window, mobile-sized simulated viewport, on-screen keyboard and page with existing fixed header. Modal preferred dimensions remain stable across tab changes.

## 16. Page/frame/browser restrictions

- Support Chrome/Brave normal web pages with valid extension injection permissions.
- Browser-internal URLs (`chrome://`, `brave://`), web stores, protected PDF viewers, inaccessible cross-origin frames and restricted pages may not permit in-page UI; do not claim otherwise.
- Browser toolbar click on an unsupported page should fail safely and, where technically possible, present a non-misleading explanation without injecting into restricted context.
- Ctrl+M may conflict with browser or site shortcuts. Test real Chrome/Brave; use extension commands registration and document limitations.
- Do not add blanket host permissions simply to make an animation work.
- Selection preservation from browser chrome must be verified in a real browser; a content script cannot read browser toolbar state directly.

## Appendix A. Types and pseudocode (illustrative only)

```ts
type ModalTab = 'correction' | 'reformulation' | 'translation';
type OpenSource = 'right-edge-handle' | 'keyboard-ctrl-m' | 'browser-action';
type ResultEntry = {
  inputRevision: number;
  operationId: string;
  output: string; // adapt to existing typed result/candidate models
  optionsFingerprint: string;
};
type ModalSession = {
  sessionId: string;
  visible: boolean;
  activeTab: ModalTab;
  sharedText: string;
  inputRevision: number;
  results: Partial<Record<ModalTab, ResultEntry>>;
  originalVerifiedSelection: unknown; // use real existing snapshot type
};

function openModal(source: OpenSource): void {
  if (state.visible) { focusExistingModal(); return; }
  const snapshot = captureExistingVerifiedSelection();
  state = newSession({
    activeTab: 'correction',
    sharedText: snapshot?.selectedText ?? '',
    originalVerifiedSelection: snapshot,
  });
  hideSemicircle();
  showCenteredModal();
}
function onSharedTextChanged(next: string): void {
  if (next === state.sharedText) return;
  state.sharedText = next;
  state.inputRevision += 1;
  state.results = {};
  invalidatePreviousPendingResults();
}
function onGenerationResponse(response: GenerationResponse): void {
  if (!state.visible || response.sessionId !== state.sessionId) return;
  if (response.inputRevision !== state.inputRevision) return;
  state.results[response.tab] = validatedResult(response);
}
function hideModal(): void {
  invalidatePreviousPendingResults();
  disposeTransientSession();
  hideCenteredModal();
  showSemicircleAtSavedY();
}
function applySafely(): void {
  const applied = existingGuardedApply(state.originalVerifiedSelection, chosenResult());
  if (!applied) { showSafeCopyOnlyFallback(); return; }
  hideModal();
  showGuardedUndoForMilliseconds(5000);
}
```

**Important:** This is conceptual pseudocode, not a replacement for actual repository types or existing dispatch/editor APIs.
